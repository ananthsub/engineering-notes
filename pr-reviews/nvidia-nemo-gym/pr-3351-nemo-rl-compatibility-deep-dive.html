Will Gym PR 3351 break current NeMo RL?

A critical review of the GenRM cohort deadline and failure-cleanup change, traced through the exact Gym revision NeMo RL pins, current NeMo RL main, and current Gym main.

Answer first

Not an API break for current NeMo RL, but not a safe blind submodule bump

Current NeMo RL already implements the identities, full-group retry, and nested sample mask that PR 3351 expects. The successful GenRM path is compatible. The failure path is intentionally behavior-changing: judge failures that previously became ordinary default scores now become zero-valued, masked failure rows.

Two cautions remain. First, a clean merge with current Gym main leaves the new standard top-level mask_sample field false while the legacy RL-specific nested mask is true. This is not a current-RL blocker—RL still masks correctly—but it is a real shared Gym contract gap for direct clients. Second, current NeMo RL GenRM recipes inherit the PR's new 300-second judge deadline while permitting 16,384 or 24,576 output tokens. That can convert slow but healthy judge calls into masked groups.

The concrete behavior change

Consider one pairwise judge call that returns HTTP 200 with an empty JSON object. The exact answer-generation inputs are unchanged. Only the disposition of the unusable judge reply changes.

This is intentionally behavior-breaking for GenRM failure cases. It is also the safer semantic choice: an unavailable judge did not measure policy quality. The relevant paths are the PR's bounded judge call and retry loop, cohort evaluation boundary, and failure cleanup.

What does not change: a completed, non-empty but malformed judge answer still falls back to configured defaults after parsing retries. Empty, unsuccessful, transport-failed, or timed-out replies become failures.

Why current NeMo RL is compatible

NeMo RL main pins Gym at 267305e…, the merged cohort-identity change that PR 3351 extends. RL itself carries the same three wire keys in its public integration constants.

Identity and replacement are aligned

The batched path stamps the three coordinates. The retry path increments the shared attempt after a retryable failure.

Mask consumption is aligned

RL reads the nested environment flag, carries it into the final batch, and sets the corresponding loss multiplier to zero. Its default is to honor flagged samples.

Compatibility here means the current code can interpret the PR's output. It does not mean every old NeMo RL release can. A consumer that neither reads the mask nor routes judge_failed rows would train on the placeholder zero.

Finding: the clean merge hides a mask contract split

High-confidence integration finding · not a current-RL blocker

PR 3351 only sets the legacy nested mask; current Gym expects the standard top-level mask

Current Gym main added BaseVerifyResponse.mask_sample specifically for unavailable judges and other infrastructure failures. PR 3351's failure path sets only instance_config.mask_sample.

A synthetic merge was conflict-free and 401 focused tests passed, but the serialized judge-failure row was:

{
  "reward": 0.0,
  "_ng_failure_class": "judge_failed",
  "mask_sample": false,
  "instance_config": {"mask_sample": true}
}

current NeMo RL consumes mask: true

Consequence: current NeMo RL is protected by its compatibility read. Gym's own collector is also protected because _ng_failure_class routes the row to the failure sidecar. A direct /verify or /run client following current Gym's standard response contract still sees false and may treat the placeholder zero as usable. The clean git merge and passing suites do not detect this semantic disagreement.

Requested fix in the shared Gym boundary: update judge_failsafe to set top-level mask_sample=true, failure_kind="judge_failed", and the human-readable reason, while retaining the nested flag for RL migration. Add one integration test that validates the serialized agent /run result against current BaseVerifyResponse. PR 3351 exposes the gap but need not own the general fix.

The operational breaking change is the new finite deadline

The PR makes collection, evaluation, and each judge request finite. The shipped judge-request value is 300 seconds. The PR's own guide notes that 16,384 output tokens at 40 tokens/second need about 410 seconds before queueing. Current RL recipes configure up to 24,576 tokens and do not override the new timeout.

This is not a Python API break. It is a runtime policy change: a previously unbounded slow call now becomes a masked full-group failure. That can reduce usable batch size, trigger replacement work, or exhaust retry budgets. It deserves explicit recipe values rather than silently inheriting 300 seconds.

# Derive these from measured queue time and minimum expected throughput.
genrm_compare_resources_server:
  resources_servers:
    genrm_compare:
      judge_request_timeout_s: <queue + max_generation + margin>
      cohort_evaluation_timeout_s: <judge_deadline + retry_sleeps + margin>

All comparisons run concurrently, so the evaluation deadline need not multiply by the number of pairs. It must still cover the slowest judge call, retry sleeps, aggregation, and scheduling delay. The concurrent comparison implementation supports that sizing rule.

Author-provided public evidence

The PR description reports complete CI, focused GenRM tests, real policy/judge calls, failure preservation, resume, and recognition by the unchanged RL mask consumer. Those claims are useful but remain author-provided; the public PR does not link a replayable full RL training artifact.

Not independently reproduced

  • Full RL training, checkpoint restart, token-capture integration, or comparative throughput.
  • A long judge generation that crosses the 300-second boundary.
  • The entire future Gym submodule delta. Current Gym main does not yet contain PR 3351. Even pinning the open PR head spans 30 commits and 190 files; current Gym main spans 55 commits and 435 files. A future post-merge bump is much broader than PR 3351.

Bump decision

Recommendation

Proceed only as a staged compatibility bump, not as a routine pin refresh

PR 3351 itself is compatible with current RL's group identity and mask behavior. The top-level mask seam should be fixed in Gym's shared failsafe, but it does not block current RL. The operational gate is to declare measured GenRM deadlines and then test the exact future Gym merge SHA that RL will pin.

  1. Wait for and pin the merged SHA. Current Gym main does not contain PR 3351. Keep the exact resulting revision; do not validate only the old PR head or today's unrelated main.
  2. Unify failure fields in Gym's shared failsafe. Assert top-level and nested masks are both true during migration, with failure_kind="judge_failed". This protects direct consumers even though current RL and Gym collection are already safe.
  3. Set explicit RL recipe deadlines. Derive them from queue latency, token ceiling, and observed minimum judge throughput.
  4. Run three end-to-end cases. Healthy judge; transient 503 that recovers without policy regeneration; persistent judge failure that yields masked rows and zero policy loss.
  5. Exercise incomplete membership. Confirm RL retries the complete group with one incremented shared attempt, not a subset under attempt zero.
  6. Validate checkpoint/restart if the target recipe uses it. The PR explicitly does not provide durable server state.
  7. Review the whole submodule range. A bump from 267305e… to a future current-main merge includes hundreds of files beyond this PR.

Bottom line: this is a deliberate failure-semantics break, not a current-NeMo-RL wire break. With the two integration gates above, it should improve correctness. Without them, the bump can silently mask healthy slow judges or expose unusable zeros to consumers that follow Gym's new top-level contract.
