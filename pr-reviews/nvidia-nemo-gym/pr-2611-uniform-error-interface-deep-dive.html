NeMo Gym review · rollout failure contract

Does PR #2611 provide a uniform rollout error interface?

A design review of Gym PR #2611 against issue #2750 and its public error-handling design documents.

PR base: c8e67b0c1f52… PR head: f55c8a0e6f08… Design snapshot: e156f4fcb857… NeMo RL reference: a43d71b31850… Reviewed 2026-08-27 UTC
Answer: PR #2611 is not merge-ready. It adds the right complete-result field, but AnySWE currently passes mask_sample twice and raises TypeError while constructing every result. The collector also includes masked rewards in final aggregate scores and mixes sidecar or omitted outcomes into progress “unmasked” scores. Beyond those blockers, one Gym producer emits contradictory top-level and nested values, NeMo RL reads only the nested value, and its newer asynchronous payload path always creates an all-ones sample mask. A safe rollout contract therefore needs producer ownership, a top-level consumer migration, explicit GRPO group policy, and documentation for both success and failure outcomes.

Start with three concrete outcomes

The field names become clear only after the caller can see the object that actually exists.

A · evaluated system scored zero 
{
  "reward": 0.0,
  "mask_sample": false
}

The verifier completed normally. Zero is valid evidence about the evaluated system and remains part of evaluation and any other downstream use.

B · complete but unusable 
{
  "reward": 0.4,
  "mask_sample": true,
  "failure_kind": "judge_degraded",
  "failure_reason": "fallback judge"
}

The real response and token sequence still exist. The caller may preserve the group slot while excluding this sample from loss or score.

C · no valid result 
{
  "outcome": "failure",
  "failure": {
    "stage": "agent_request",
    "delivery": "may_have_received"
  }
}

There is no honest reward or sample. A placeholder reward=0 plus mask_sample=true would erase delivery and retry information.

Design source: missing versus unusable results and the three verifier fields.

What PR #2611 adds—and what it does not

Useful foundation

BaseVerifyResponse gains mask_sample: bool = False. Any typed agent response can now expose the same top-level key. SWE and AnySWE mirror their legacy nested value into it.

base response · SWE mirror · AnySWE mirror

Still outside this PR

The PR does not add the outcome union, a serializable failure record, or run_outcomes(). A request exception still escapes run_examples() before managed routing can attach it to the input row.

current library boundary · proposed boundary

Figure 2 — One returned dictionary moves through both caller paths

The new field survives the HTTP result dictionary. That solves field placement, but it does not turn pre-result exceptions into caller-visible values.

The field description is too long, training-specific, and hard to scan

The current text is an ordinary comment, not a docstring, and it will not appear as the field's description in Pydantic's generated schema. It is formatted as two dense prose blocks above two small fields. The double-backtick markup around reward also has no useful effect in a Python comment.

Current framing

It turns a data contract into training advice

Phrases such as “Gym states the fact and stops there” and “frameworks legitimately differ” sound conversational but do not sharpen the type's meaning. The list of loss masking, episode resampling, group statistics, and group dropping overfits the field to RL training. Gym itself needs the field to compute evaluation scores and coverage, and other callers may persist, inspect, retry, or filter the result.

The phrase “this reward is the policy's” is also too narrow. The evaluated system may be an agent, model, workflow, or external harness.

Recommended framing

Describe the result, not every possible consumer action

State the completeness invariant, explain what the boolean means, and preserve legitimate zero rewards. Put operational guidance in user documentation rather than the schema field description.

mask_sample: bool = Field(
    default=False,
    description=(
        "Whether this completed sample should be excluded "
        "from evaluation scores and other downstream quality "
        "calculations because its reward is not a valid "
        "measurement of the evaluated system's behavior."
    ),
)

failure_reason: Optional[str] = Field(
    default=None,
    description=(
        "Human-readable explanation of a failure or "
        "degradation reported for this result."
    ),
)

This wording is caller-neutral: Gym evaluation, NeMo RL, and direct library users all receive the same fact. Their handling belongs in the caller contract. If Field(description=...) is not desired, the same two sentences still work as short field comments.

current field comments

Two defects must be fixed before merge

Blocking · AnySWE

Every result construction passes mask_sample twice

SWEBenchMetrics already declares mask_sample, so metrics.model_dump() contains that key. The PR also supplies mask_sample=… explicitly before expanding the dictionary. Python rejects the duplicate keyword before Pydantic can validate the response.

TypeError: AnySweVerifyResponse()
got multiple values for keyword argument 'mask_sample'

The computed decision is written to metrics.mask_sample. Construct the response from that single source, then add an end-to-end /run test. The current focused tests exercise the helper and schema but never instantiate this result shape.

metrics schema · computed mask · duplicate constructor arguments

Blocking · scoring

Masked infrastructure rewards still change published scores

Managed collection persists masked complete results in the main JSONL and sends every persisted result to /aggregate_metrics. Generic aggregation averages reward without consulting mask_sample. A valid reward of 1 plus a masked infrastructure reward of 0 therefore publishes mean/reward=0.5, not the unmasked score 1.0.

The progress path has a related boundary error: sidecar failures and _ng_no_persist results enter its unmasked counter whenever their top-level flag is absent or false. Progress and final aggregation need one explicit population definition—normally persisted, complete, unmasked results—plus separate coverage counts for masked, failed, and omitted outcomes.

routing followed by progress counting · persisted results sent to aggregation · generic aggregate path

A known producer contradicts the new top-level field

The conversational-tool-use simulation agent was already identified in the PR description as a nested mask_sample producer, but it is not migrated. Its transient failure builder sets only instance_config.mask_sample=true. Pydantic fills the newly inherited top-level field with its default, false.

{
  "_ng_failure_class": "transient",
  "reward": 0.0,
  "mask_sample": false,
  "instance_config": {
    "mask_sample": true
  }
}

This exact object was reproduced from the agent's existing 429 failure path at the reviewed head. The new contract comment tells consumers to prefer the top-level field, so a direct caller following the contract reads the wrong polarity.

Orange dashed elements are the reproduced path. The sidecar routing marker and sample-usability flag answer different questions, but the metric code checks only the false top-level flag.

There is a second compatibility effect. A default BaseVerifyResponse serializes mask_sample=false, and the generic reward profiler converts booleans to numbers. A one-result reproduction produced five new aggregate series: mean, max, min, median, and std/mask_sample, all zero. Therefore “an unmodified environment behaves identically” is not true for aggregate metric output.

The uniform interface should be an outcome union, not one overloaded response

PR #2611 can remain the complete-result half. Issue #2750 needs a second top-level variant for invocations that end before a valid result exists.

Figure 4 — Target caller contract

The producer reports facts. The caller owns retry, replacement, masking, dropping, and stop policy. Neither side has to infer policy from free text or a zero reward.

Complete-result rules

  • mask_sample answers only whether this complete result is usable.
  • failure_kind is a stable category.
  • failure_reason explains this occurrence to a person.
  • Do not infer retryability or delivery state from these fields.

Invocation-failure rules

  • Attach failure data to the original input row.
  • Preserve stage, delivery state, retry guidance, and identity.
  • Cross process and Ray boundaries with bounded plain data.
  • Never synthesize a reward, response, or token sequence.

Who should set mask_sample now

The layer that first knows a complete result is unusable should set the top-level field. Later layers may only promote false to true; they must not clear an upstream decision. This creates one monotonic rule across resources servers, agents, and rollout finalization.

Resources server

Verification failed after a real trajectory exists

Set mask_sample=true when a judge is unavailable, verification generation fails, a tool or simulated user fails independently of policy quality, or a fallback score is not trustworthy. Keep false for a legitimate policy failure, including reward zero.

Agent harness

The harness invalidated an otherwise complete result

Preserve the resources-server value and OR in harness-owned failures such as an incomplete captured trajectory or an agent timeout that still leaves a real, internally consistent response. Write the decision only at the top level.

Rollout collector

Finalization proves the token record is unusable

Promote the flag when correlation loses a model call or produces an ambiguous token chain. The token-capture finalizer already uses this pattern. It must preserve a prior true.

Do not set the flag when no valid result exists

A request that never reached the agent, a lost session with no trustworthy response, an OOM before a result, or a reset failure belongs in RolloutFailureRecord. Until run_outcomes() exists, keep the existing failure routing marker and ensure training callers reject that row; do not make a synthetic response look complete merely by adding mask_sample=true.

NeMo RL needs two consumer fixes, not only a new key lookup

On public NeMo RL main, _extract_mask_sample_flags() reads only full_result.instance_config.mask_sample. A direct reproduction passed top-level true with nested false and received false; reversing the values produced true. NeMo RL therefore follows the legacy field, not PR #2611's contract.

Required compatibility fix

Read and validate the top-level field

Read full_result.mask_sample first. For one compatibility window, read the nested value only when the top-level key is absent. If both exist and disagree, mask the sample and emit a conflict metric or warning. Require actual booleans; bool("false") is true in Python.

current nested-only extractor · nested-only tests

Required asynchronous fix

Carry usability into the replay payload

Add a typed mask_sample fact to Completion, populate it in AsyncNemoGymRolloutImpl._result_to_completion(), and set each payload row's sample_mask from it. The current record_to_train_batch() creates torch.ones for every completion, so this path cannot honor either field location.

completion conversion · all-ones asynchronous sample mask

GRPO must choose a group policy before computing statistics

The synchronous path currently calculates each prompt group's baseline and standard deviation with an all-ones mask, then zeros the flagged row's loss later. This prevents a flagged row from contributing gradients, but its infrastructure reward still changes the advantages of valid siblings. That reproduces the distortion described by issue #2750.

Recommended NeMo RL policy: replace a flagged completion before admitting the prompt group. If replacement is exhausted, calculate baseline and standard deviation from unmasked completions and drop the whole group when too few valid members remain. “Loss only” may remain an explicitly named legacy mode, but it should not be described as excluding the sample from group statistics.

baseline uses all rows · loss mask is applied later

The existing env.should_mask_flagged_samples switch should evolve into a policy choice such as replace, exclude_from_statistics, drop_group, or temporary loss_only. Once Gym's contract is narrow, “ignore the flag and train anyway” is no longer a safe interpretation of a complete but unusable result. Report masked, replaced, conflicting, and dropped-group counts separately.

Documentation must define the contract at three boundaries

Gym producer guide

How environment authors classify an outcome

Add a canonical page beside the resources-server and agent authoring guides. Define the complete-result precondition, all three fields, the monotonic ownership rule, and examples for policy zero, degraded judge, incomplete token capture, and no-result infrastructure failure.

Gym caller guide

What managed and library APIs return

Document the success/failure outcome union, persistence sidecars, stable rollout identity, and caller ownership of retry, replacement, masking, group dropping, and coverage. Link this page from run_examples(), reward profiling, and external-agent-harness documentation.

NeMo RL integration guide

How training consumes the fact

State field precedence and the nested deprecation window. Explain the selected GRPO group policy, behavior when every completion is masked, synchronous and asynchronous parity, configuration values, and metrics. Show that reward zero with false remains trainable.

Also add a short migration note: producer releases write both locations with identical values; consumers read top-level first; conflicts fail closed and are observable; a named release removes nested writes and fallback reads. Keep mask_sample out of generic reward aggregation and publish intentional coverage metrics instead.

Review questions before treating this as the shared interface

1. Will the contract explicitly require a complete result?

The current comment names lost sessions, unavailable judges, OOM-killed containers, and reset timeouts. Some of those paths cannot provide a real response and complete token fields. The existing OSWorld empty-result path makes the ambiguity concrete: its comment says the rollout “couldn't even start,” but it constructs a placeholder response and sets mask_sample=true. The shared design says those cases must return RolloutFailureRecord and must not include mask_sample. Narrow the comment and tests to “a complete result exists but is unusable,” then use a separate outcome for pre-result failures.

PR wording · existing placeholder path · design rule

2. Will the field description be caller-neutral and schema-visible?

The current comment reads like guidance written specifically for an RL trainer and does not become Pydantic schema documentation. Replace it with a short Field(description=...) that defines validity for evaluation scores and other downstream quality calculations. Move examples of retry, loss masking, resampling, and group handling to the caller documentation.

current wording

3. Will every known producer move to the top level in the same compatibility window?

The conversational-tool-use failure path now serializes opposite top-level and nested values. Its resources-server sibling also keeps its masking decision only under instance_config. AnySWE's attempted migration raises because the key is supplied both explicitly and through metrics.model_dump(). Fix AnySWE, migrate both conversational-tool-use paths, and add regression tests that assert complete serialized dictionaries. Search all existing mask_sample and inverse valid_sample producers before documenting “prefer the top level.”

agent failure payload · resources verifier payload · test misses top-level assertion

4. Which rows define the “unmasked reward” denominator?

The current progress counter includes every result whose top-level mask flag is false, including returned _ng_failure_class sidecar rows and _ng_no_persist rows. Final aggregation excludes those routing classes but still includes complete rows with mask_sample=true. Neither path measures the score after infrastructure failures are removed. Define the set first—normally persisted complete, unmasked results—and test the same mixed batch through progress metrics and final aggregation.

storage classes · metric denominator

5. Is mask_sample a control field or a generic score?

The default serializer plus generic boolean aggregation adds five metric series even when nothing is masked. Either filter contract fields from generic reward profiling and publish intentional coverage metrics, or document the expanded metric schema and update the compatibility claim. A regression should cover an unmodified typed environment with all defaults.

generic conversion · current field tests

6. Where is the caller contract documented?

The implementation comment cannot carry the full policy boundary. The design's completion criterion requires one documented contract for environment authors, managed evaluation, direct callers, and training adapters. The page should show the two outcome variants, the three complete-result fields, and which layer owns retry, persistence, masking, replacement, group statistics, and coverage.

component migration completion criterion

7. Which NeMo RL policy is part of the rollout contract?

Changing the field lookup fixes transport but not GRPO semantics. Today the flagged reward participates in baseline and standard-deviation calculation before its loss is zeroed, and the asynchronous replay payload ignores the flag. Choose replacement, exclusion, or group dropping; implement the same policy in synchronous and asynchronous paths; and test a mixed prompt group where an infrastructure zero would otherwise change valid samples' advantages.

legacy field lookup · asynchronous all-ones mask · group statistics

Practical consequence

Keep PR #2611 as the field-placement foundation, but do not merge it until AnySWE can construct a result and both progress and final scoring use the intended result population. Then fix the reproduced producer polarity, migrate every known complete-result producer, and narrow mask_sample to complete results. Update NeMo RL to consume the top-level field in both rollout paths and choose a group-statistics policy. Finally, complete issue #2750 with run_outcomes() and RolloutFailureRecord. That gives evaluation and training callers one stable boundary without turning missing infrastructure outcomes into ordinary zero-reward samples.
