How prompt cohort identity survives retries from NeMo-RL to GenRM

A focused review of NeMo-RL PR #3861 and NeMo Gym PR #2814: what stays stable, what changes on retry, and where stale or duplicate responses are stopped.

RL head: 0c22e3e0dc43… Gym head: 7f93814b014c… Snapshot: 2026-08-27 UTC
Answer after independent re-review: the retry IDs work when RL sends one prompt group at a time. They do not work in RL's synchronous Gym path when a batch contains more than one prompt. RL gives every row in the batch the same group_id. Gym then sees different prompts with the same group ID and rejects the later prompt. The Gym PR also breaks older requests that identify a prompt without the new group and rollout fields.

RL puts different prompts in the same GenRM group

This happens in RL's synchronous Gym helper. The inference engine is asynchronous, but these callers wait for the whole batch and use run_nemo_gym_rollout_sync().

  1. GRPO repeats each prompt num_generations_per_prompt times.
  2. RL sends the full repeated batch to run_nemo_gym_rollout_sync().
  3. The helper passes the total batch size as num_generations.
  4. _prepare_nemo_gym_rows() uses that number as the size of one prompt group.
  5. Every row in the batch receives the same group_id, even when the rows came from different prompts.

If the batch contains prompt A and prompt B, Gym receives both under the same group ID. GenRM records prompt A first. It then rejects prompt B because the prompt text changed inside the same group. If two tasks happen to have the same prompt text, the error can be harder to see because unrelated tasks may be compared as one group.

This path is used by synchronous GRPO training, GRPO validation, PPO, distillation, and SyncRolloutActor. A batch containing only one prompt is not affected.

Correctness blocker

Use the response count for one prompt when assigning IDs

The code needs two separate numbers:

  • num_generations_per_prompt tells RL which rows belong to one GenRM group.
  • input_batch.size tells RL how many total rows it must wait for before the synchronous call returns.

Add num_generations_per_prompt to run_nemo_gym_rollout_sync(). Pass the training or validation value from each caller. Use it when _prepare_nemo_gym_rows() assigns group_id and rollout_index. Continue waiting for every row in input_batch.size, and return all completed prompt groups in their original input order.

Changing only the existing num_generations argument is not enough. The current synchronous helper also uses that argument to make the whole batch return as one result. The fix must separate ID grouping from result collection.

One identity tuple crosses six concrete boundaries

1. RL creates the logical group once per generate_and_push call. group_id = G and the starting attempt come from the prompt metadata or are initialized once. A separate tq_group_id is reserved inside the retry loop.
rollout_manager.py L1289–L1324
2. RL copies the logical coordinates into the attempt input. The original sample is not mutated. Each whole-group retry receives the same G and the current attempt number.
rollout_manager.py L1333–L1346
3. RL expands the prompt into stable sibling slots. All rows share G and the attempt. Their rollout_index values are 0..N-1.
async manager row builder · batch rollout row builder
4. Gym's agent preserves unknown row extras into /verify. The simple agent run and verify request models allow extra fields. The verify request is built from the run body plus the model response.
extra-field models · run → verify call
5. GenRM resolves (G, attempt), then claims one member per slot. An identical duplicate joins or reuses the slot. A different response digest for the same slot returns 409. A newer attempt advances the watermark and fails active older attempts.
slot registration and duplicate handling · watermark and supersession
6. Gym maps rewards by slot and echoes trusted dispatch identity. GenRM sorts slots before comparison and publishes a reward map. The shared rollout boundary overwrites any agent-provided identity with the coordinates from the dispatched row.
ordered evaluation and publication · trusted transport echo

Worked example: three siblings, one partial failure

Use one logical prompt group G-42 with three siblings. Attempt 0 reaches GenRM with slots 0 and 2, but the group fails before slot 1 completes. RL replaces the whole group. The replacement keeps G-42, advances the attempt to 1, and uses a fresh Transfer Queue ID.

Figure 3 — Old and replacement responses cannot form one cohort

Blue solid boxes are the accepted replacement cohort. Orange dashed boxes are superseded state. Purple boxes are physical Transfer Queue transactions.

The critical separation is deliberate: group_attempt protects GenRM's semantic cohort, while tq_group_id protects the physical Transfer Queue transaction. Reusing one identifier for both would either mix old GenRM responses or collide with old queue rows. This mechanism is sound only after RL forms the correct prompt-group boundary.

What the public evidence proves — and does not

Demonstrated in unit tests

RL preserves logical identity across its retry loop. Gym rejects conflicting duplicates, caches identical duplicates, separates attempts, rejects stale arrivals, and returns rewards by slot. These tests exercise correctly formed cohorts; they do not cover a heterogeneous synchronous batch.

Demonstrated at boundaries

The simple agent allows extra fields into /verify. Gym's shared collection boundary overwrites returned identity with the dispatched row's identity.

transport boundary test

Not publicly demonstrated

No test in these PRs injects a partial failure through the actual RL → Gym agent → GenRM path and proves that the final committed prompt uses only one attempt's rewards.

Current checks are not green. At this snapshot, Gym lint failed because Ruff reformatted one test file. RL's lock check failed on an OpenAI dependency conflict after the Gym submodule update. These failures do not disprove the identity logic, but they mean the revisions are not merge-ready and provide no green full-suite signal.

Concrete questions for reviewers

1. Can RL preserve prompt-group boundaries in the synchronous path?

The current wrapper treats the entire repeated batch as one group. This must be corrected before the new Gym precedence rule is safe for synchronous GRPO or validation batches containing multiple prompts. A regression test should use two distinct prompts with two generations each and assert two group IDs with indices [0,1] in each.

group construction · incorrect group-size argument

2. Can the pair add one cross-repository failure-injection test?

The unit tests prove individual functions. They do not prove that a partial old cohort, a whole-group retry, the agent's extra-field forwarding, the Gym transport echo, and RL's final commit all compose correctly. A two- or three-sibling test that loses one result after GenRM receives it, then observes attempt 1, would resolve this gap.

Relevant seams: RL partial-row redispatch · Gym agent run path · GenRM supersession

3. Where is the single-worker requirement enforced?

The cohort map, watermark map, and locks are instance-local private attributes. If siblings or attempts are routed to different workers, no worker sees the complete cohort and no watermark can reject stale traffic on another worker. The PR description documents one worker, but the protocol itself cannot detect a multi-worker deployment. A startup guard, routing guarantee, or explicit deployment test would turn that requirement into an enforceable contract.

process-local registries · test proving server instances do not share cohorts

4. What owns a future partial-rollout checkpoint?

A coupled RL and Gym restart is safe today because uncovered prompts are regenerated into a fresh Gym process. It is at-least-once recovery, not partial continuation: the rollout checkpoint persists task ordinals and completed replay groups, but not active group_id, group_attempt, per-slot responses, or GenRM members. Future partial rollout checkpointing needs one durable authority for the logical transaction. The simplest contract is for RL to persist the stable group, next attempt, expected cohort size, and per-slot durable response references, then replay a complete higher attempt into an empty GenRM after restart.

checkpoint cut · persisted rollout state · frontier restore

Recommended review order

  1. Fix synchronous grouping first: cohort size must be generations per prompt, not transport-batch size.
  2. Settle compatibility: either retain prompt-only append behavior or narrow the backward-compatibility claim.
  3. Verify the forwarding and retry boundary: row extras must reach /verify, and one replacement attempt must return rewards to the right slots.
  4. Review GenRM deployment: enforce one worker or provide shared, group-sticky state.
  5. Define future restart ownership: partial rollout checkpoints need durable logical transaction and per-slot state.

Practical consequence: the tuple design prevents retry mixing after a cohort is formed correctly. The current synchronous path does not form those cohorts correctly, so the RL fix must separate prompt-group size from batch size before the pair is safe to merge.
