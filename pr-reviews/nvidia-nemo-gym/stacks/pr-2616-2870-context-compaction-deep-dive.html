Answer first

Current Gym has two correct but disconnected truths. The model server’s merged lineage path proves whether a request is an exact token continuation. The compaction agent knows whether it intentionally rewrote context. A rewrite is therefore correctly UNRESOLVED at the model server even though the agent knows it is logically related.

The fix is not to weaken lineage verification. Each call needs two edges: a logical parent for reward and terminal ancestry, and an optional physical parent for exact-prefix token continuity. Compaction preserves the first and clears the second.

Finalization must join the two views. It selects one rewarded logical path, partitions that path whenever the physical edge is absent, verifies each physical segment independently, and emits ordinary flat tensor rows. It does not send a forest to the trainer.

TransferQueue can carry the result without becoming graph-shaped. The inference worker stages one digest-bound call record per model call in a staging partition. A SingleController finalizer later publishes one flat training row per physical segment under one logical rollout group.

A fully black-box harness cannot reveal why an unresolved request occurred. The gateway can observe a token discontinuity, but it cannot generally distinguish compaction from retries, branches, or auxiliary calls. Exact full-rollout recovery therefore requires an explicit parent receipt, a protocol-native parent ID, or a narrowly qualified single-flight inference rule.

The current PRs do not implement this join. RL #3910 still rejects data_plane.enabled=true, Gym #2278 still models one physical parent_call_id, and its finalizer returns one LinearizedRow.

Current Gym state: two meanings of “parent”

#2180 / #2181: physical parent

The model server receives a request and asks LineageStore whether its model-authored history identifies exactly one committed earlier call. resolve_node returns only ROOT, RESOLVED, or UNRESOLVED.

A fingerprint finds candidates. The full conversation digest then proves that the earlier context was unchanged. #2181 supplies the winning parent’s exact cumulative tokens and requires generation-time prefix proof before storing a child delta.

This parent means: “the child’s physical training sequence extends these exact tokens.”

#2616 / #2870: logical parent

The compaction session retains full SemanticHistory while materializing a smaller view for the next call. It assigns a stable prepared_request_id, segment_id, and context epoch before dispatch.

After the call, completion capture records expected_append_compatible and the applicable compaction_event_id.

This parent means: “the later action belongs to the same semantic rollout and receives the same terminal reward.”

The apparent conflict is intentional. A compacted request should fail #2180’s unchanged-context proof. The unsafe fix would be to reinterpret every UNRESOLVED result as a valid continuation. The safe fix is to retain the logical edge while starting a new physical root.

The missing schema distinction

  parent_call_id = exact physical token parent

required unified record
  logical_parent_call_id  = previous action on rewarded path
  physical_parent_call_id = exact-prefix token parent, or null
  transition              = root | append | rewrite

  compaction_event_id      = authorization for a rewrite boundary

Gym #2278 demonstrates why this distinction matters. Its CallRecord has one parent_call_id: a parent requires token_in; no parent requires a text root. Its terminal walk follows that same field and returns one contiguous row. That is sufficient before compaction but cannot express “logically follows C2, physically starts S1.”

Why finalization, specifically?

Before the rollout ends, the agent does not know the rewarded terminal call. The model server does not know which served response the harness kept. The inference worker knows exact tokens but not semantic compaction policy. The SingleController finalizer is the first component that can fence the attempt, select terminal ancestry, join the three evidence sets, publish every child row, and retire staging only after durable acceptance.

“Segment-aware finalization” therefore does not mean teaching the trainer to execute a graph. It means converting a graph-shaped evidence set into an ordered list of verified linear rows before training sees it.

What changes when the agent harness is a black box?

The gateway still sees every model request and response. It can prove physical continuity from engine-observed tokens. What it cannot generally observe is the semantic reason for a discontinuity or which earlier branch the black box intended to continue.

Practical black-box options

  1. Best: use a model-gateway receipt that the black box echoes on the next request. This need not expose compaction internals; it only names the logical predecessor.
  2. Protocol-native: preserve a field such as previous_response_id across the rewrite when the harness API supports it.
  3. Narrow fallback: declare the harness single_flight and forbid retries, auxiliary calls, and branching. The gateway may then link a discontinuity to the immediately preceding completed call, but the evidence must remain labeled inferred.
  4. General black box: do not guess. A token discontinuity proves a new physical root, not its logical parent. Mask the logical rollout or train only the independently proven terminal segment.
An explicit “compaction event” is not always required. What finalization actually needs is a trustworthy logical-parent edge plus proof that the physical edge broke. A cooperative compaction agent provides both directly. A black box may instead provide a parent receipt. Without either, complete reward attribution is unknowable in the general case.

One rollout, two physical traces

Use one small two-call rollout. The first model call sees prompt tokens [101, 102] and samples [201]. Compaction rewrites the second prompt to [101, 301], which is not a prefix continuation of [101, 102, 201].

NeMo-RL recomputes that digest, checks the declared rewrite against token and media continuity, and creates rollout-7:trace-000000 plus rollout-7:trace-000001.

How the finalizer creates physical traces

The capture set may be a forest because retries and branches can produce calls that never reach the scored answer. The finalizer first uses logical_parent_call_id to walk backward from the terminal call. Only that selected path receives the reward. Non-selected branches are retained for audit or retired; they do not become training rows.

selected logical path: C1 → C2 → C3 → C4

start S0 with C1's full observed prompt + generation

C2.physical_parent == C1
  verify exact cumulative prefix
  append C2's staged token delta to S0

C3.physical_parent == null and C3.logical_parent == C2
  verify an authorized rewrite boundary
  close S0
  start S1 with C3's full compacted prompt + generation

C4.physical_parent == C3
  verify exact cumulative prefix
  append C4's staged token delta to S1

publish [S0, S1] as two rows owned by logical rollout R7

A physical row starts with the complete prompt observed at that segment’s root. Prompt and tool carry tokens are masked from policy loss. Each model generation contributes trainable token positions and generation-time logprobs. Append children add only their verified deltas. A rewrite child must never borrow its logical parent’s prefix.

The fail-closed rule is simple: a missing physical edge creates a segment only when a trusted rewrite or qualified black-box boundary explains it. A claimed physical edge with a prefix, digest, or media-order mismatch poisons the rollout rather than creating another segment.

Layer 1 — #2616 adds semantic compaction without erasing logical history

Gym #2616: agent-owned state and exact evidence

mergedopt-in agentvLLM adapter

The new simple_agent_with_compaction owns the entire mechanism. Existing simple_agent and shared Gym request models are not changed by this layer.

1. The semantic history is the durable truth

ContextCompactionSession creates one SemanticHistory per rollout, appends initial context and seed observations, then selects either a rolling HistoryController or a TurnChunkedHistoryController. See the pinned session constructor.

The model-facing request is a materialized view. Model output is also appended to the full semantic history after successful evidence capture, so compaction does not make the logical rollout incomplete. The session exposes the complete append-order output through output_items.

2. Append compatibility is based on the last generation’s exact tokens

When the next materialized view is append-compatible, the session constructs required_prefix_token_ids from the previous prompt plus sampled tokens. That happens in _prepare_once. The dedicated vLLM model adapter accepts that field and refuses to reconstruct missing training evidence with a later tokenization request; see the adapter’s fail-closed path.

3. Rewrites become explicit boundary events

A recency policy can remove old images or reasoning blocks. A turn-chunked controller freezes one compacted base for several actions, then opens another chunk. It records the eligible action IDs and completion evidence IDs when finalizing a chunk; see chunk acknowledgement and finalization. A non-prefix-compatible next view advances the segment and carries a boundary event, rather than pretending that one flat physical sequence still exists.

4. Guard tokenization is advisory; generation evidence is authoritative

Optional guards can measure total tokens, active images, and projected vision tokens before a call. A chunk may close early and recompact once. The accepted model response still supplies the authoritative prompt IDs, generated IDs, and logprobs. Guard admission and successful response recording are separate stages.

Maintenance cost: #2616 introduces a substantial agent-local protocol: semantic unit lineage, content-addressed media, policy decisions, chunk records, guard outcomes, completion evidence, and model identity contracts. The isolation protects ordinary agents, but consumers must still agree on the exported subset.
“Bounded” describes duplication, not total rollout size. The transport drops validation-only copies, but complete logical output, unique media assets, lineage, chunks, boundaries, and one metadata record per call remain. Prompt-token arrays on successive output items can also grow with accumulated context. Recency only bounds configured image groups and reasoning blocks; tool results and ordinary text still need optional total-token guards.

What the digest does—and does not do

ModelCallMetadata.from_observed omits three arrays from the sidecar and computes generation_evidence_digest over them:

{
  "prompt_token_ids": observed.prompt_token_ids,
  "sampled_token_ids": observed.sampled_token_ids,
  "sampled_logprobs": observed.sampled_logprobs
}

The digest prevents the small metadata record from silently drifting away from the arrays. It does not replace the arrays. They remain as prompt_token_ids, generation_token_ids, and generation_log_probs on the trainable output item. The new README says this directly in the rollout trace evidence section.

The verifier still sees full evidence

run sends the rich model response to /verify when verification is enabled. Only after reward processing does the common return path build the transport response. When verification is skipped, there is no verifier call, but the same transport projection is returned.

How NeMo-RL #3910 consumes the unified contract

RL #3910 is not merely compatible by name. Its final commit changes ingestion from the old contract to rollout_trace_contract, and its PR body explicitly says it must not merge before Gym #2870.

1. Gym remains the generation-evidence boundary

NeMo-RL reads caller-owned rollout and group IDs, validates them against the contract, counts trainable output items, and requires one metadata record per call. It then recomputes the digest from each output item’s canonical arrays. See contract and digest validation.

2. The planner rejects undeclared discontinuities

build_rollout_trace_plan validates token/logprob types and lengths, media IDs, call identity, append compatibility, boundary use, segment identity, and rollout ownership. In strict mode a prompt rewrite without a matching boundary is an error. A boundary where no rewrite occurred is also an error.

3. Ingestion reconstructs canonical physical message logs

For each trace start, NeMo-RL resets seen_token_ids, then converts newly seen prompt tokens into a non-trainable user message and sampled tokens into a trainable assistant message. The canonical arrays are popped from the raw output item during this conversion; see physical-log reconstruction.

4. Logical reward semantics survive physical expansion

GRPO advantage computation happens once per logical rollout. Batch preparation validates complete comparison groups and rollout ownership, creates one row per physical trace, projects the same logical advantage to each row’s eligible action tokens, and only then pads to data-parallel × microbatch divisibility.

5. Both legacy training loops are wired

The synchronous loop calls the physical-trace preparation helper before ordinary flattening at the sync data-processing stage. The older asynchronous loop does the same at its data-processing stage, with extra replay-group identity and policy-version checks in trace_replay.

The unified TQ shape

TransferQueue does not need a forest schema. It needs two clearly separated lifecycles. The capture-staging partition holds untrusted per-call evidence keyed by rollout_id/model_call_id. The canonical rollout partition holds verified physical training rows keyed by deterministic trace IDs.

Required controller semantics

  1. One logical reservation, dynamic child count. The reservation begins before rollout. Finalization determines trace_count after terminal-path selection.
  2. Deterministic child identities. Use keys such as R7:trace:0 and R7:trace:1. Store logical_rollout_id, trace_index, trace_count, and segment_id as tags or metadata.
  3. Atomic readiness, not necessarily atomic writes. Child writes may happen separately, but the replay buffer must not expose the group until every declared child is durable.
  4. Logical reward accounting. Compute one reward and GRPO advantage per logical rollout. Project that scalar to eligible action tokens in each physical row, as #3910 already does in process.
  5. Logical scheduler accounting. Optimizer tensors use the physical row count; scheduler progress and comparison-group completeness use the logical rollout count.
  6. Conditional retirement. Clear staged call rows only after canonical child publication succeeds. Keep poisoned, incomplete, or digest-invalid evidence for diagnosis.

The existing TQ API is already row-shape-agnostic: kv_first_write accepts caller-minted sample IDs and optional tags. The missing work is the SingleController group lifecycle and the segment-aware finalizer, not a graph tensor format.

What “remove token IDs and logprobs from the Gym agent path” requires

RL #3456 already demonstrates the heavy-data hop: TQTokenSink.stage writes exact token, mask, and logprob deltas before acknowledging the model call. Gym #2278’s model-server ledger carries only digest-bound commit coordinates and response identity.

The unified path should use that custody boundary. The compaction agent returns semantic output, terminal identity, segment metadata, and logical edges. It does not return canonical token arrays. The finalizer fetches those arrays from TQ, verifies them against the Gym ledger, and only then creates physical rows.

Review questions that remain

1. Will the capture schema separate logical and physical parents?

Gym #2278 currently uses one parent_call_id for exact token continuity. Compaction requires a later call to retain logical ancestry while becoming a parentless physical root. Reviewers should require an explicit two-edge schema and tests that reject an undeclared missing physical edge.

2. How does compaction intent reach the model server before generation?

#2870 exports boundary metadata after the call. Prefix admission occurs before the call. A unified implementation needs an authenticated per-request CaptureTransition carrying logical call identity, logical parent, transition kind, segment, and boundary digest. The model server must strip this control metadata before backend inference and continue verifying physical continuity independently.

3. Which black-box guarantee is supported?

A general black box does not expose enough information to recover logical ancestry across a rewrite. Reviewers should choose among a required parent receipt, protocol-native parent ID, a documented single-flight-only inference mode, or fail-closed masking. Completion order must not silently become lineage for concurrent or branching harnesses.

4. What makes a logical TQ group ready and recoverable?

One rollout can produce a dynamic number of physical child rows. The controller needs a durable group descriptor, deterministic child IDs, expected child count, and a readiness transition after every child write. Checkpoint and replay recovery must restore the group atomically rather than exposing a partial set of traces.

5. Which merged Gym revision will RL #3910 pin?

The refreshed RL head still references Gym c3bac963, which predates the compaction agent. The PR must update its gitlink to a merged Gym revision containing #2870, then rerun the exact integration at that combined revision.

6. Can one public integration fixture exercise the full join?

The needed regression should run an append call, a declared rewrite, and another append through worker-owned TQ staging. It should then finalize two physical rows under one logical reservation, project one GRPO advantage to both, checkpoint and reload the ready group, and prove staged evidence retires only after canonical publication.

Practical review order

  1. Preserve #2180/#2181’s fail-closed physical lineage and exact-prefix proof.
  2. Define the per-request transition contract that carries #2616’s logical compaction intent to the model server.
  3. Separate logical and physical parent fields in the capture ledger and staged records.
  4. Make finalization select terminal logical ancestry and return an ordered list of verified physical rows.
  5. Add the SingleController logical-group lifecycle over TQ child rows.
  6. Qualify black-box behavior explicitly; do not infer general lineage from request order.
  7. Then update #3910’s Gym pin and run one cumulative integration fixture.

Bottom line

The two Gym mechanisms should remain separate authorities. #2180/#2181 decides whether exact tokens continue. #2616/#2870 decides whether a semantic rewrite was intentional. A unified call record must preserve both decisions instead of weakening either one.

The finalizer builds the forest only long enough to select one terminal logical path. It then partitions that path into ordinary linear physical traces. TransferQueue stores those flat rows and one logical group descriptor; the trainer never consumes an arbitrary graph.

For cooperative agents, an authenticated per-call transition supplies the missing join. For black-box agents, a parent receipt or equivalent protocol field is required for exact recovery. Without one, the safe behavior is masking or terminal-segment-only training.

This is still proposed work. Refreshed RL #3910 remains a legacy in-process consumer with an explicit data-plane rejection, while Gym #2278 and RL #3456 provide the worker-owned TQ staging primitives that the unified finalizer can reuse.
