How Gym context compaction reaches NeMo-RL training

A maintainer’s map of Gym #2616, its contract cleanup in #2870, and the public NeMo-RL consumer in RL #3910.

Answer first

#2616 supplies the missing trace semantics. It keeps an append-only logical history, compacts only the next model-facing view, records exact generation evidence, and marks every intentional prompt rewrite.

#2870 supplies the usable wire contract. Verified and verification-skipped rollouts now return the same bounded rollout_trace_contract plus digest-backed model_call_metadata.

NeMo-RL #3910 consumes that contract on the legacy GRPO driver paths. It validates each digest, splits a logical rollout into physical traces, computes one logical GRPO advantage, projects it to every physical row, and supports both synchronous GRPO and the older async replay path.

The exact NeMo-RL #3910 checkout is not runnable with this feature yet. Its Gym submodule still points to c3bac963, a revision from before simple_agent_with_compaction existed. The code is wire-compatible with #2870, but the dependency pin is not.

It is not compatible with NeMo-RL’s SingleController / TransferQueue path at this revision. SingleController requires data_plane.enabled=true, while #3910 explicitly rejects physical-trace training when that flag is true.

It also does not remove token IDs or generation logprobs from Gym’s exported /run payload. #2870 removes their second copy from completion_evidence; the canonical arrays remain on ordinary response output items and still cross the Gym → NeMo-RL boundary.

Layer 1 — #2616 adds semantic compaction without erasing logical history

Gym #2616: agent-owned state and exact evidence

mergedopt-in agentvLLM adapter

The new simple_agent_with_compaction owns the entire mechanism. Existing simple_agent and shared Gym request models are not changed by this layer.

1. The semantic history is the durable truth

ContextCompactionSession creates one SemanticHistory per rollout, appends initial context and seed observations, then selects either a rolling HistoryController or a TurnChunkedHistoryController. See the pinned session constructor.

The model-facing request is a materialized view. Model output is also appended to the full semantic history after successful evidence capture, so compaction does not make the logical rollout incomplete. The session exposes the complete append-order output through output_items.

2. Append compatibility is based on the last generation’s exact tokens

When the next materialized view is append-compatible, the session constructs required_prefix_token_ids from the previous prompt plus sampled tokens. That happens in _prepare_once. The dedicated vLLM model adapter accepts that field and refuses to reconstruct missing training evidence with a later tokenization request; see the adapter’s fail-closed path.

3. Rewrites become explicit boundary events

A recency policy can remove old images or reasoning blocks. A turn-chunked controller freezes one compacted base for several actions, then opens another chunk. It records the eligible action IDs and completion evidence IDs when finalizing a chunk; see chunk acknowledgement and finalization. A non-prefix-compatible next view advances the segment and carries a boundary event, rather than pretending that one flat physical sequence still exists.

4. Guard tokenization is advisory; generation evidence is authoritative

Optional guards can measure total tokens, active images, and projected vision tokens before a call. A chunk may close early and recompact once. The accepted model response still supplies the authoritative prompt IDs, generated IDs, and logprobs. Guard admission and successful response recording are separate stages.

Maintenance cost: #2616 introduces a substantial agent-local protocol: semantic unit lineage, content-addressed media, policy decisions, chunk records, guard outcomes, completion evidence, and model identity contracts. The isolation protects ordinary agents, but consumers must still agree on the exported subset.
“Bounded” describes duplication, not total rollout size. The transport drops validation-only copies, but complete logical output, unique media assets, lineage, chunks, boundaries, and one metadata record per call remain. Prompt-token arrays on successive output items can also grow with accumulated context. Recency only bounds configured image groups and reasoning blocks; tool results and ordinary text still need optional total-token guards.

Layer 2 — #2870 makes verification status irrelevant to trace encoding

Gym #2870: one transport shape

openone commitbreaking rename

This layer follows #2616 after merge. It intentionally replaces the recently added names and discriminators instead of preserving aliases.

Before #2870

Verification runs: context_compaction_contract has schema_version: 3; output is bounded and uses model_call_metadata. The direct parent’s return branch makes the split explicit.

Verification skipped: the same field has schema_version: 2; the response retains full completion_evidence, agent_input, and seed_obs.

Consumers therefore branch on a reward-control decision to decode the rollout trace.

After #2870

Both cases expose rollout_trace_contract with no lifecycle schema_version, mode, or format.

Both cases use the bounded model_call_metadata representation.

Only the actual verifier request receives full completion_evidence.

The key implementation boundary is now explicit. ContextCompactedResponse is the rich internal/verifier model. ContextCompactedTransportResponse and build_transport_response remove agent_input, seed_obs, and completion_evidence, project image payloads out of output content, and replace each observed completion with bounded metadata.

This is specifically an agent /run transport guarantee. The compaction agent’s direct /v1/responses self-call still constructs the rich response before run decides whether to send it to the verifier and then projects it for the caller.

What the digest does—and does not do

ModelCallMetadata.from_observed omits three arrays from the sidecar and computes generation_evidence_digest over them:

{
  "prompt_token_ids": observed.prompt_token_ids,
  "sampled_token_ids": observed.sampled_token_ids,
  "sampled_logprobs": observed.sampled_logprobs
}

The digest prevents the small metadata record from silently drifting away from the arrays. It does not replace the arrays. They remain as prompt_token_ids, generation_token_ids, and generation_log_probs on the trainable output item. The new README says this directly in the rollout trace evidence section.

The verifier still sees full evidence

run sends the rich model response to /verify when verification is enabled. Only after reward processing does the common return path build the transport response. When verification is skipped, there is no verifier call, but the same transport projection is returned.

How NeMo-RL #3910 consumes the unified contract

RL #3910 is not merely compatible by name. Its final commit changes ingestion from the old contract to rollout_trace_contract, and its PR body explicitly says it must not merge before Gym #2870.

1. Gym remains the generation-evidence boundary

NeMo-RL reads caller-owned rollout and group IDs, validates them against the contract, counts trainable output items, and requires one metadata record per call. It then recomputes the digest from each output item’s canonical arrays. See contract and digest validation.

2. The planner rejects undeclared discontinuities

build_rollout_trace_plan validates token/logprob types and lengths, media IDs, call identity, append compatibility, boundary use, segment identity, and rollout ownership. In strict mode a prompt rewrite without a matching boundary is an error. A boundary where no rewrite occurred is also an error.

3. Ingestion reconstructs canonical physical message logs

For each trace start, NeMo-RL resets seen_token_ids, then converts newly seen prompt tokens into a non-trainable user message and sampled tokens into a trainable assistant message. The canonical arrays are popped from the raw output item during this conversion; see physical-log reconstruction.

4. Logical reward semantics survive physical expansion

GRPO advantage computation happens once per logical rollout. Batch preparation validates complete comparison groups and rollout ownership, creates one row per physical trace, projects the same logical advantage to each row’s eligible action tokens, and only then pads to data-parallel × microbatch divisibility.

5. Both legacy training loops are wired

The synchronous loop calls the physical-trace preparation helper before ordinary flattening at the sync data-processing stage. The older asynchronous loop does the same at its data-processing stage, with extra replay-group identity and policy-version checks in trace_replay.

Compatibility with NeMo-RL v2 architecture

  • Gym #2870 contract ↔ RL #3910 ingestion: field names, digest construction, identity checks, and boundary semantics line up.
  • RL #3910 checkout as pinned: its Gym gitlink is still c3bac963, which has no compaction agent or unified trace contract.
  • Legacy synchronous GRPO: physical rows are prepared inside grpo_train.
  • Legacy asynchronous GRPO: replay preserves complete logical groups and policy provenance before physical expansion.
  • Ordinary non-compacted rollout: it remains on the existing path; physical materialization activates only when a rollout contains more than one physical trace.
  • SingleController: no integration is added to single_controller.py.
  • TransferQueue/data plane: split physical traces are rejected when data_plane.enabled=true.
  • “Token IDs/logprobs off the Gym path”: not achieved; canonical arrays still travel in the Gym response.

Why TransferQueue needs a separate design

SingleController registers a long-lived TransferQueue partition before concurrent producers begin. Its schema contains flat input_ids, generation_logprobs, masks, rewards, and later policy deltas; see SC_ROLLOUT_SCHEMA_FIELDS. The first write stores tensor rows and sample metadata through kv_first_write.

Compaction changes the row cardinality after rollout: one logical rollout can become two or more physical rows, while GRPO comparison groups and rewards remain logical. A TransferQueue implementation therefore needs an explicit decision about when expansion happens, how sample IDs map logical parents to physical children, which controller metadata owns that map, and how replay/checkpoint recovery treats the group atomically. #3910 implements those decisions only in in-process BatchedDataDict preparation.

What “remove token IDs and logprobs from the Gym path” would require

The current contract assumes that Gym is the authority for the exact prompt seen by each model call. NeMo-RL verifies a digest against arrays carried in that same response. Removing those arrays from the Gym boundary requires another publicly defined authority: for example, a generation-side or TransferQueue record keyed by immutable call IDs, with Gym transporting only those IDs, boundary metadata, media ordering, and digests. The consumer would then join the records before trace planning and prove that the joined arrays match Gym’s digest.

Neither Gym PR implements that join. RL #3910 also reads the arrays directly from Gym output at ingestion. The accurate conclusion is “validation-only duplication removed,” not “token evidence removed from Gym.”

Review questions that remain

1. Which merged Gym revision will RL #3910 pin?

This is a concrete merge blocker, not an architectural preference. The pinned RL head still references Gym c3bac963, which predates the compaction agent. The PR must update its gitlink to a merged Gym commit containing #2870, then rerun the exact integration at that combined revision.

2. Is SingleController a merge requirement or a planned follow-up?

The current implementation cannot run there. If SingleController is the target production architecture, reviewers need a public design for logical-to-physical sample IDs, TransferQueue schema changes, replay-group atomicity, checkpoint metadata, and where expansion occurs. A regression should run a compacted Gym rollout through run_grpo_single_controller with data_plane.enabled=true.

3. Where should exact generation arrays live long term?

#2870 removes duplicate arrays but leaves the originals on Gym output. If the architectural goal is to keep token IDs and logprobs entirely out of the Gym transport, the producer and consumer need a durable join key and a failure rule for missing, duplicated, stale, or digest-mismatched generation-side records.

4. Can the exact merged-Gym integration be replayed publicly?

RL #3910 declares a hard dependency on #2870 and says the Gym dependency must be updated after merge. The strongest end-to-end validation uses a harness that is not in either public PR. Before merge, a public or CI-contained deterministic fixture should demonstrate the exact #2870 wire payload entering #3910 and producing the expected physical training rows.

5. Is an unversioned public contract intentional beyond this rollout?

Removing versions that represented internal lifecycle stages is correct. But an unversioned, extra="forbid" wire model makes any future required field a coordinated breaking change. Reviewers should decide whether the field name itself is the compatibility discriminator or whether a genuine protocol revision mechanism is still needed.

6. Which generation-contract fields must NeMo-RL enforce?

Gym’s generation contract exports component identities, incomplete reasons, and a training_eligible signal. Other metadata adds processor fingerprints, policy spans, and evidence source. RL #3910 validates the canonical-array digest and trace continuity but does not enforce every exported provenance field. Reviewers should document which fields are informative and which are required to reject training.

Practical review order

  1. Accept or reject the #2870 wire contract first: one field name, one transport shape, canonical-array digest binding.
  2. Review RL ingestion against that exact contract: identities, digest, media order, and boundary validation.
  3. Review logical-to-physical semantics: one reward and advantage per rollout, one or more physical training rows.
  4. Decide whether legacy sync/async support is enough. If SingleController is required, treat the TransferQueue work as missing functionality rather than incidental follow-up polish.
  5. Only then assess the larger #2616 policy and history machinery, because its exported trace contract is what constrains every downstream path.

Bottom line

#2616 and #2870 form a coherent Gym-side design: semantic history remains complete, physical rewrites are explicit, exact generation arrays stay authoritative, and #2870 makes the exported envelope independent of verification. RL #3910 contains a credible consumer for the legacy synchronous and asynchronous GRPO drivers, and focused ingestion tests pass.

The exact RL head is not yet integrated because its Gym submodule pin predates both compaction contracts. That pin must move to a merged revision containing #2870 before the public PR can be tested as a complete checkout.

For the v2 architecture named in the question, compatibility is incomplete. SingleController is TransferQueue-based, and the public consumer PR deliberately blocks that route. The token/logprob optimization is also narrower than “off the Gym path”: duplicate validation evidence is gone, but canonical token IDs and logprobs still travel through Gym and are consumed directly by NeMo-RL.
