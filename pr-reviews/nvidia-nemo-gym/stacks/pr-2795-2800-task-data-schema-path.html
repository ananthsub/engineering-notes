How NeMo Gym validates task data before rollout

A two-PR stack turns each resources server’s implicit dataset-row expectations into a Pydantic schema that data tooling can inspect and enforce during collation.

Answer first. PR #2795 owns the mechanism: find the resources server, normalize one row into task-owned fields, load its TaskData, validate, then warn or fail. PR #2800 supplies the missing schemas, expanding the mechanism from six examples to all 114 schema-bearing resources servers. Runtime verification does not change; malformed rows are moved earlier in the lifecycle, from rollout to data preparation.

The failure moves from rollout to collation

Before the stack

A dataset row has no tool-readable declaration of its task-owned fields. The resources server’s request model is the nearest contract, but data tooling cannot discover it without importing server code and dependencies.

Pydantic request models that use the default extra="ignore" can silently discard a typo. Missing or mistyped required values surface only when a rollout reaches the server.

After both PRs

Each resources server can expose one dependency-light TaskData symbol. gym dataset collate resolves the owning server and checks each row before it enters the collated dataset.

The default is warn. error blocks collation on type failures or conflicting duplicate values. off preserves the prior path.

Important boundary. These PRs validate task-owned dataset fields. They do not replace the resources server’s runtime request model, change verify(), or move rows into the future task_data container yet.

Each PR has one distinct job

#2795: establish the protocol and path

Adds: schema discovery, dynamic loading into a Pydantic TypeAdapter, row normalization, reports, collate policy, owner resolution, gym env schema, and six examples.

Contract: schemas describe a flat future task shape. Framework keys are excluded. Legacy verifier_metadata contents are lifted before validation.

Guardrail: schema modules may use only lightweight imports, and every model must choose extra="allow" or extra="forbid"; silent extra="ignore" is banned.

Evidence: behavior-focused unit tests plus the public CI suite. The PR also reports live collate checks and a routing comparison, but does not attach a public replay artifact.

#2800: make the protocol repository-wide

Adds: 108 task_data.py files. Combined with the six examples below, the repository has 114 schemas.

Handles: plain models, discriminated unions, open envelopes, model reuse across server families, minimal pointer schemas, and field metadata for consumers and legacy locations.

Assumes: #2795’s loader, normalization, validation report, and collate policy are accepted unchanged.

Evidence: the PR reports 153 files and 1,003 rows checked with zero errors or ambiguous duplicates. CI proves the schemas import and conform, but the full data sweep is not committed as a replayable check.

The worked row uses distinct values so each decision is visible. It is a multiple-choice task with answer C, an 8,000-token provenance bucket, and one misspelled optional field used later to expose the review gap.

1

Resolve the schema owner

Collation starts from the config entry that declared the dataset. A resources-server declaration owns its own data. An agent declaration follows its resources_server reference. A self-contained agent has no external schema owner and is skipped.

4

Dispatch to the multiple-choice variant

eval_type="multichoice" selects Ruler2MultichoiceTaskData. The required answer is a string, so "C" passes. The model allows extra keys by design.

For a plain root model, the validator separately counts undeclared fields. For this root union, it does not. Therefore the misspelled lenght is accepted and omitted from the report. That is the concrete review question below.

5

Apply the collation policy

off skips construction of the validator. warn prints a report when validation is dirty or plain-model unknown keys exist. error raises only when the report is not clean. On success, the original row—not the normalized Pydantic output—is written to the prepared JSONL file.

Pinned source: validate, write, warn, or fail

Legacy rows take one extra normalization step

A row such as {"verifier_metadata": {"expected_city": "Paris"}} becomes {"expected_city": "Paris"} for validation. The schema remains flat, while legacy_location: "verifier_metadata" records today’s wire location. Equal top-level and nested duplicates are accepted. Different values make the report dirty, with the top-level value retained.

Pinned source: flat weather schema and legacy annotation · Pinned source: duplicate behavior tests

The important decisions are explicit

The validator does not replace row contents with Pydantic’s parsed output. This matters for compatibility: validation is observational unless the configured policy raises. The collated row keeps task fields in their current locations.

What the public evidence proves—and does not

Demonstrated in committed tests

  • Framework keys are removed and legacy metadata is spliced.
  • Equal duplicate values are harmless; conflicting values are dirty.
  • Plain models report unknown keys without treating them as validation errors.
  • Agent-declared datasets resolve to their referenced resources server.
  • Every schema imports with the allowed dependency set and rejects extra="ignore".

Demonstrated by public CI

This proves repository checks pass. Green CI alone does not prove every schema matches every dataset row.

Reported, but not publicly replayable here

#2795 reports 2,922 core tests, a zero-difference routing gate, and live warn/error checks. #2800 reports a sweep of 153 files and 1,003 rows with zero errors and zero ambiguous duplicates.

Those claims are public in the PR descriptions, but the stack does not commit the sweep command, result file, or a repository-wide data-validation test. A reader cannot reproduce that evidence from the changed files alone.

Not established by this stack

The stack does not show that future dataset edits remain schema-valid, that every external or generated dataset matches, or that all schema annotations are complete for migration tooling. It also does not move validation to error by default.

The PR descriptions explicitly leave per-server error flips and documentation to follow-up work.

Concrete review questions

Root unions do not report undeclared keys

Observed behavior. _declared_field_names() returns field names only when the adapter’s root type is a single BaseModel. It returns None for a root Annotated[Union[…]]. TaskDataValidator.validate_row() counts unknown keys only when that set is not None.

Real case. RULER2’s root TaskData is a discriminated union, and both variants use extra="allow". A row with optional length misspelled as lenght still has all required fields, so Pydantic accepts it and the report stays silent.

Consequence. The stack’s promise that warn mode reports undeclared keys does not hold uniformly. Typos in optional or provenance fields can survive collation for root-union schemas.

Resolution to request. Add a union-focused regression test and either collect the selected variant’s declared fields after discriminator resolution or state clearly that unknown-key reporting is unsupported for root unions.

Pinned source: root unions return no declared-field set · Pinned source: unknown-key counting is conditional · Pinned source: extra-allow root union

Evidence request. Preserve the reported 1,003-row sweep as a public, repeatable command or test. Without it, future schema and dataset changes can drift while the import and extra-mode enforcement tests remain green.

Practical consequence and review order

Review #2795 first because it defines ownership, normalization, failure policy, and what counts as clean. Then review #2800 as data: sample one server from each schema pattern, verify its wire request model and verify() path, and confirm requiredness plus field locations. Finally, run the repository-wide row sweep and retain the result.

If both layers land unchanged, NeMo Gym gains an inspectable schema for task-owned fields and a compatibility-preserving warning path during collation. It does not yet guarantee fail-closed data preparation. That begins only when individual servers switch task_data_validation to error.
