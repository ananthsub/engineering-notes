How reusable task data enables runtime agent swapping

A critical review of the data-routing stack in PRs #2710–#2732, then the separate swappable-agent stack in #2640, #2641, and #2661.

Short answer. The data stack changes a dataset row from “run this exact agent instance” to “this task came from this task/verifier source.” The run then chooses an agent, stamps that choice into materialized inputs, and keeps it in outputs as provenance. The swappable-agent stack changes a different layer: it loads a selected harness implementation and composes it into the environment’s existing agent instances. The second stack does not strictly require the first today—it preserves old instance names precisely so baked agent_ref rows still route—but the data stack removes that compatibility constraint and makes swapping, re-routing, and fan-out coherent runtime operations.

1. The data stack first: identity moves out of the row

The central change is ownership. A source or collated row should describe a task. It should not permanently choose the process that executes the task. PR #2717 makes the resources-server or self-contained-agent declaration the data owner, and collate writes that owner as task_source. It explicitly removes incoming agent_ref while preparing the row (pinned producer code).

#2710merged

Make legacy rows re-routable

agent_map overrides a specific baked agent or all rows through _default. agent_name becomes shorthand for the default mapping (code). Agent names are validated before requests begin, avoiding partial dispatch.

#2713merged

Resolve task sources and expand runs

The resolver inverts configured agent→resources-server edges and requires exactly one candidate (code). fan_out creates per-agent copies during run preprocessing, not in the stored dataset.

#2717merged

Produce clean collated data

Datasets may live on a resources server. Collate stamps task_source, strips legacy routing, and allocates distinct prepared paths for repeated declarations (code). Reverify also routes directly from the task source (code).

#2724open

Teach benchmarks and scaffolding

Benchmark discovery accepts resources-server-owned datasets and chooses an agent by explicit pin, legacy declaration, or unique reverse edge (code). New scaffolds emit the decoupled layout.

#2732open

Migrate repository data and configs

The mechanical layer removes row-level agent_ref, moves declarations to their resources servers, introduces fan-out for duplicate-agent comparisons, and removes aliases that existed only to satisfy stale stamps. It is the adoption layer, not a new runtime mechanism.

2. The runtime routing contract

PR #2713 applies routing before dispatch. For a row that carries both fields, an agent_ref.name map entry wins over a task_source entry. Then _default applies. Without a map, a legacy agent_ref remains authoritative; otherwise task_source is resolved. Fan-out targets are final, and repetition can key on either the resolved target or the original routing basis (preprocessing code).

Important boundary. Direct callers of run_examples get task-source resolution and validation, but not agent_map, fan_out, or num_repeats. They must call preprocess_examples first (API contract). This matters for trainer integrations that bypass the CLI pipeline.

3. Why this matters for swapping—and what is not a hard dependency

It is tempting to say agent swapping is impossible while rows contain agent_ref. The code is more nuanced. PR #2640 deliberately retains each environment’s top-level agent instance name when it replaces the inner implementation. Its own comment says why: changing the instance name would break prepared data whose route is baked in (composition code).

So the composition stack can swap a harness under legacy data. But it can only do so by maintaining an alias-like shell:

row agent_ref = "math_simple_agent"
top-level instance remains "math_simple_agent"
inner implementation changes simple_agent → hermes_agent

The data stack removes that hidden requirement. Once a row says task_source: math_resources, routing can be recomputed from the current graph. The selected harness no longer needs to masquerade behind a historical row stamp. This is what makes one dataset reusable across a renamed agent, a different harness, or a multi-agent comparison.

4. How the swappable-agent stack builds on the foundation

#2640

Configuration transform

Composition runs after includes, command-line overrides, and inheritance are merged, but before missing-value validation (parse order). It replaces every target agent instance, not one chosen target.

#2641

One flag, two namespaces

In serve mode, --agent names an agent config asset and appends its path. Under --no-serve, it names a running top-level instance and becomes +agent_name (translation).

#2661

Verifier-side allowlist

A resources server may declare requires_agent. The guard compares the selected implementation type with that list before composition (guard). Missing or unreadable declarations are permissive.

5. Where the stacks meet

Three identities share the word “agent.” task_source is the stable task/verifier owner. A runtime agent instance is a top-level config key used by dispatch, agent_map, fan-out, and no-serve routing. An agent implementation is the inner responses_api_agents key used by composition and requires_agent. A serve-mode asset name is not automatically a valid runtime-map target: composition removes the unbound template instance and installs its implementation under the preserved environment instance names.

The clean mental model is “route, then implementation.” The current CLI blurs the boundary: serve-mode --agent chooses an implementation asset, while no-serve --agent invokes the data stack’s route-all behavior. Serve composition also replaces every target instance. A fan-out list can still name several preserved runtime instances, but all of those instances receive the same selected harness implementation, with only carried-over bindings such as model and resources server distinguishing them. That is the most important cross-stack UX decision to settle.

6. Critical findings and concrete review requests

1 · Merged defect: reverify aggregation loses the resources-server dimension

PR #2717 correctly groups reverified results by (agent, resources server), but each returned entry contains only agent_ref. Export keys are then built only from the agent name. If one agent handles task sources from two resources servers, the second group overwrites the first in metrics_to_log, and the JSON entries cannot identify which server produced either result (pinned code). This exact concern was raised in the public review and remains present at the merged head.

Consequence: exported metrics can silently report only one verifier group. Request: include the resources-server name in each aggregate entry and in exporter/console keys; add a two-task-source, one-agent regression test.

2 · Merged defect: reverify preflight can check a different verifier set than row routing uses

Row-level /verify routing treats a resources-server task_source as authoritative. The preflight reverify_mode guard instead builds its server set from agent configuration edges (row resolver, preflight). A row remapped by task_source can therefore reach a verifier that was never checked.

Consequence: an unsupported verifier can run without requiring --force and without the unsafe output prefix. Request: derive preflight servers from the actual rows with the same resolver used for /verify; add a task-source-remapped unsupported-server test.

3 · Open blocker: composition can discard command-line overrides after they win the merge

PR #2640 merges command-line values at highest priority, then replaces each target’s entire inner agent config with a copy of the source. Only three target keys survive. A CLI override aimed at another target field can therefore win the merge and still be deleted by composition (merge then compose, replacement). An unresolved public review thread demonstrates this with a target max_turns override.

Consequence: the resolved run can differ from the user’s explicit override without an error. Request: define override paths after composition, or reject overrides against replaced branches; add an end-to-end parser test for an overridden non-binding field.

4 · Open blocker: --agent changes both meaning and accepted names with --no-serve

Serve mode accepts an asset/config name. No-serve mode accepts a running instance name and routes every row to it through PR #2710. A public review gives two concrete regressions: an explicitly selected harness overlay can be replaced by a later base config, and documented instance-style names fail serve-mode asset lookup (public evidence). GitHub also currently marks #2641 conflicting with its parent.

Consequence: adding or removing --no-serve changes the referent namespace and the operation. Request: use separate flags for harness composition and row routing, or require an explicit mode/name prefix; cover existing documented commands before merge.

5 · Contract gap: the benchmark agent: pin does not participate in runtime task-source resolution

PR #2724’s benchmark discovery and preparation honor a dataset-level agent pin (discovery). Runtime resolution in #2713 does not inspect dataset declarations; it only inverts agent→resources-server edges and errors on two candidates (runtime resolver).

Consequence: the advertised disambiguator can make listing/preparation succeed while a newly collated task-source row still fails at run time. Request: either propagate the pin into run routing or state that agent_map is the runtime disambiguator; add a full prepare→collate→run test with two agents on one resources server.

6 · Reproducibility gap: the migration’s strongest proofs are not committed

The narrow row transformation is independently inspectable: the 83 changed JSONLs contain 736 rows, with exactly 736 top-level agent_ref removals and no other row-content or row-count changes. The broader claims are different. PR #2732 reports repository-wide parse sweeps, routing replay, trainer compatibility, and six live rollout patterns, but the one-shot verification tool is not committed and no public run artifacts are linked. Reviewers cannot rerun those exact invariants from the head.

Consequence: future rebases cannot independently prove that the large mechanical diff still changes only declared fields. Request: commit a deterministic verification script or attach machine-readable public outputs keyed to the head SHA.

7 · Adoption gap: direct rollout callers do not receive run-level routing behavior automatically

The public API deliberately separates preprocess_examples from run_examples. Existing direct integrations that call only the latter can run task-source rows, but cannot exercise map, fan-out, or repeat semantics. PR #2732 lists downstream adoption as follow-up work rather than part of this stack.

Consequence: “swappable from the same data” is true for the CLI path before it is true for every trainer path. Request: gate migration claims for each integration on a committed test that invokes preprocessing and dispatch together.

8 · Guard scope: compatibility is serve-composition-only, opt-in, and implementation-type-wide

PR #2661 explicitly allows a swap when requires_agent is absent, empty, or unreadable. It compares the selected inner implementation name, not an agent asset flavor or complete configuration (code). The guard runs during serve-mode composition. No-serve --agent, agent_map, and fan-out only validate that a target is an existing runtime agent instance; they do not consult requires_agent.

Consequence: the guard proves only that an annotated verifier allows that broad implementation type on one entry path; it does not establish compatibility for runtime re-routing or arbitrary custom configurations. Request: call it a serve-time allowlist assertion, define whether map/fan-out should enforce the same contract, and decide whether first-party resources servers must all declare it.

Recommended review and landing sequence

  1. Fix the two merged reverify defects: aggregate identity and preflight/row-routing server-set mismatch.
  2. Settle #2724’s single runtime disambiguation contract: dataset pin, agent_map, or one clearly documented precedence chain.
  3. Rebase #2640→#2641→#2661 onto the merged task-source foundation. Re-run the complete stack checks; #2641 is not currently mergeable.
  4. Resolve command-line override precedence in #2640 and split or clarify the two meanings of --agent in #2641.
  5. Add one cumulative test: one task-source dataset, two available harnesses, serve-mode composition, no-serve routing, fan-out, reverify, and aggregate output identity.
  6. Only then land #2732’s repository-wide migration, with a rerunnable migration verifier pinned to the final combined behavior.
Practical consequence. The architecture is moving in the right direction: reusable data identifies tasks; the run chooses routes; outputs record provenance; composition chooses implementations. The remaining risk is not the core separation. It is that three adjacent selectors—benchmark agent pins, routing maps, and harness composition—currently use overlapping names and incomplete precedence rules. Reviewers should settle those seams before treating the migration as the final state.
