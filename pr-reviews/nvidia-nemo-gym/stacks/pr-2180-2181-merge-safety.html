What the two PRs do

#2180 — parent identity becomes a request-time decision

Before this PR, the trajectory builder inferred which recorded call a continuation extends by token-prefix matching at build time. #2180 moves that decision to request time: when a tagged request arrives at the model server, resolve_parent fingerprints the model-authored turns of the request and verifies the candidate parent's conversation-context digest. The outcome is a tri-state stamped onto the record: ROOT (no model-authored turn), RESOLVED (exactly one verified parent), or UNRESOLVED with a reason (no_match, ambiguous, resolver_unavailable, lookup_error). The builder then re-verifies every claimed link by hashing the child's prompt prefix against the parent digest, so a wrong RESOLVED becomes parent_digest_mismatch → masked, never a silent join. Multi-worker deployments share lineage through the capture JSONL itself under file locks; a startup gate refuses num_workers > 1 without a process-shared store.

Assumes from below: the merged terminal-attribution join (#2675/#2676) — this PR extends the builder to take a terminal_call_id anchor. Changed by above: #2181 consumes the resolution to supply prefixes; in #2180 alone, parent_tokens is stamped but unconsumed.

#2181 — the engine receives the parent's exact tokens, with proof

For a RESOLVED continuation, the model server attaches required_prefix_token_ids — the parent's exact cumulative token ids — as the last preprocessing step before dispatch, and marks prefix_requested. After generation, _verify_generation_prefix demands generation-time proof: the served prompt token ids must extend the requested prefix exactly, or the model call fails with RuntimeError — a hard failure, unlike capture errors, which never fail a call. Unsupported paths (completions API, native responses, missing token-id return) are rejected at config-validation time. Separately, an opt-in delta_records mode stores only the prompt suffix beyond the parent's cumulative tokens; the reader rebuilds full prompts iteratively (cycle guard, 10,000-step depth bound, digest re-verification; broken chains are excluded and masked).

The per-call path after both merge

The blocking finding: delta records are mis-read by today's main

The re-cut of #2181 collapsed its schema constants to TOKEN_ENTRY_RECORD_SCHEMA_VERSION = 1, MIN = 1 (the previously validated revision wrote version 5 with a floor of 3). prompt_is_delta is therefore a new field on a version-1 record — and main's TokenEntry uses extra="allow", so main's reader accepts the record and treats the stored suffix as the full prompt. main has no lineage fields to warn it: prefix inference roots the fragment, the terminal join attributes it (it is the last call, with a corroborated response_id), and the consumer delivers it unmasked.

Confirmed yield regressions in #2180 — safe direction, but decide them explicitly

#2180 changes the mask policy: a terminal path containing an unresolved_boundary is now "broken" (builder.py:381), where main only checked quarantine — terminal attribution can no longer rescue unresolved ancestry. Running identical inputs through both revisions:

The mask-fraction kill switch defaults off (max_mask_fraction: None), so nothing aborts; the run silently yields zero trainable samples from old records.
  • Compaction: the in-tree exact-prefix compaction flow (vllm_model_with_compaction / simple_agent_with_compaction, #2616) rewrites the message list, resolves UNRESOLVED, and now masks even though its token prefix digest-verifies — the PR defeats a feature on main whose entire point is a token-exact chain across compaction. Options: permit a digest-verified token-prefix join across an UNRESOLVED boundary, or add an explicit-parent declaration from the compaction agent.

Both regressions flip samples main delivers today into masked samples — the safe direction (never wrong tokens), which is why they are should-fix rather than blocking. But they are silent at the sample level, so they need an explicit decision, not an accidental merge.

Performance on the critical path

Parent resolution runs once per model call, sequential with generation, off the event loop (resolve() wraps _resolve in asyncio.to_thread); untagged traffic pays nothing. The target load is 16,000 concurrent requests. The head under review includes the parent-token reuse optimization: the chain walk happens over in-memory metadata, all backend references load in one batched operation (_materialize + the _load_entries hook), and a globally token-bounded per-rollout cache keeps the last verified parent (max_cached_tokens = 8_000_000).

In production each rollout generates for seconds between resolves, so the load is an arrival rate: 16,000 in-flight ÷ mean call duration D.

  • Capacity per worker process ≈ 690–830 resolves/s typical (410–480/s at 80k-token context), GIL-bound on laptop cores — server CPUs will do better. Required: D=30 s → 533/s (one worker suffices); D=10 s → 1,600/s (2–3 workers); D=5 s → 3,200/s (4–5 workers). The #2180 design already mandates a process-shared store for num_workers > 1, and capacity scales linearly across worker processes; size for ≤70% utilization to keep the tail flat.
  • The materialized-parent cache is globally bounded, and 16K rollouts overflow it. 8M tokens ≈ ~550 typical-length rollouts per process (≈36 bytes/token in-process). With 16K rollouts on few workers the cache thrashes — but a miss is now a single batched read, and measured entries-per-resolve stayed 1.0 throughout. For delta-heavy deployments at high per-worker residency, either raise max_cached_tokens (≈0.3 GB at the default; sizing knob exists on both store constructors) or accept periodic batched chain reads. With 16K spread over W workers, per-worker residency is 16K/W — at W=8 the default cap covers a meaningful fraction of typical-length rollouts.
  • External backend (TQ) unchanged in shape: 2 RTTs per resolve steady-state, and the new _load_entries hook lets a TransferQueue adapter fetch a cold chain in one batched read — the k-sequential-RTT cold case is gone by contract. RL #3837 currently sidesteps Gym-side materialization entirely (its worker fetches prefixes from TQ), keeping Gym on the metadata path.
  • File-descriptor and lock behavior at load: two opens per resolve (~1,400 opens/s at capacity) and per-rollout flocks — no cross-rollout lock contention; the 256 lock stripes put ~8 rollouts per stripe at 2,048 concurrent per worker, visible in the saturation tail but not in throughput collapse.

Method: benchmark drives the real code paths (TokenCaptureStore.append → resolve() via asyncio.to_thread, with stamp_continuation/stamp_lineage as the sink performs them); backend latency injected via time.sleep; instrumented store counts batch loads, entries loaded, and cache state; every continuation asserted RESOLVED. Numbers from local SSD on an M2 laptop — treat them as conservative floors for throughput, and re-check the file-store constants on the target shared filesystem. One incidental validation: an early benchmark version echoed assistant content at a different length than recorded — resolution failed closed with no_match rather than matching approximately.

Hashing assumptions for parent identity

Parent identity rests on two hashes: assistant_fingerprint (model-authored turns only — typed content parts plus tool calls with canonicalized arguments, reasoning excluded) selects candidates, and conversation_digest over the child's first context_len items (every turn, tool results included, plus the request envelope pseudo-turn carrying system prompt and tool schema) verifies the match. Both are SHA-256, domain-separated, length-delimited per field — no concatenation ambiguity. The safety question splits cleanly:

Where wrong acceptance is possible — effectively nowhere, with one documented nuance

  • A fingerprint collision alone cannot deliver wrong tokens: the builder independently re-verifies every claimed link by hashing the child's prompt prefix against the parent's token digest (builder.py:188) — acceptance requires two independent SHA-256 agreements over different domains. Empty context digests fail closed; ambiguity refuses.
  • The one real nuance: when several candidates share identical (digest, cum_len) — identical-token retries — the resolver picks min(call_id) deterministically. Token-exact by construction, but the two retries are distinct generations: their recorded logprobs can differ (nondeterministic kernels, or a weight refit between retries), and the child physically extended one specific retry. The delivered chain uses the chosen entry's logprobs wholesale. This is an accepted approximation for importance sampling, not a token-correctness bug — it should be stated in the docs rather than discovered.

Where legitimate parents are rejected — yield assumptions, silent at the sample level

  • Seeded assistant history masks entire task classes (verified gap). If a dataset row's input already contains assistant or function_call items — multi-turn pivot datasets derived from prior rollouts, few-shot prompts with assistant demonstrations — the very first call has a non-empty fingerprint, finds no recorded candidate, and resolves UNRESOLVED no_match: every rollout of that task masks. #2180 has no escape hatch for this; the related #2775 tree carries one (an empty-ledger check that roots seeded history as a text root), which is the fix shape. Until then this is a silent 100%-mask cliff per affected task.
  • Byte-exact echo: the fingerprint assumes the harness echoes assistant text exactly. Dialect differences are normalized and pinned by golden vectors across all three dialects, tool arguments are compared canonically, and reasoning is excluded — but a harness that re-wraps or trims assistant text breaks the chain → masked.
  • Envelope stability: matching deliberately includes the system prompt and tool schema, so a harness that registers tools dynamically mid-rollout (or rewrites instructions per turn) breaks context verification → masked. Correct for safety; a known yield cost for dynamic-tool harnesses.
  • Version skew: entries with a different fingerprint_version are skipped during indexing, so a mid-rollout upgrade masks the resumed tail — relevant to partial-rollout resume across deployments.

Every violated assumption lands on the masked side — the unsafe direction is guarded twice, the safe direction is where the silent costs live. That is the right trade for training correctness; the seeded-history case is the one that needs code, not documentation.

The TQ stack (#2774–#2776) and RL #3837

The TransferQueue lane is related, not dependent: it declares #2349's branch as base, but its content was cut from the pre-rebase revision of this stack. Consequences measured at the pinned heads:

  • 23 carried commits re-cut from lane A (11 patch-identical; the rest drifted by the dropped review-response commits and base-gap contamination). A merge simulation of #2776 against #2181's head conflicts in 20 files.
  • Schema fork: the TQ tree kept the old v5/min-3 ladder that #2180/#2181's heads deliberately collapsed to v1 — its version comments no longer describe what will merge.
  • It pre-dates merged terminal attribution: no terminal.py, no response_id on TokenEntry (moved to the staging layer's CallRecord), and #2776 re-implements the witnesses join on CallRecord — two parallel terminal-attribution implementations would coexist in a merged tree. One owner must be chosen.
  • RL #3837 installs Gym's StagingSink inside the vLLM worker, fetches miss-prefixes from TQ (fetch_prefix_token_ids), and forwards only token-free custody (ng_capture with staging-chain keys) over HTTP. It pins Gym submodule SHA d9ad9d2e — an older #2278-line cut whose staging surface is wire-identical to #2776 except one error-string line wrap. Merging #2180/#2181 cannot move that pin; the pin's problem is staleness (its .gitmodules claims branch = main, which is currently fiction).

Recommended merge order

  1. Fix the #2181 schema stamp (delta entries → version 2, ceiling 2) — two constants plus a cross-version test.
  2. Decide the two #2180 yield regressions (legacy-record masking; compaction masking) and the fingerprint-module duplication; add the release note for the custom-sink startup break.
  3. Merge #2180, then #2181 — conflict-free against main@f7bca4ddc; review-complete otherwise.
  4. Rebase #2774–#2776 onto the new main: drop the 23 carried commits, adopt schema v1, restore TokenEntry.response_id, and make the staging attribution delegate to (or explicitly supersede) main's terminal join.
  5. Repoint RL #3837's submodule pin to the rebased #2776 head — its imports are confined to the wire-stable staging surface — then land the TQ lane bottom-up, and #3837 last.
Consequence for the reviewer. Nothing in either PR can put wrong tokens into a training row — every uncertain path masks or fails loudly, and that property was re-verified, not assumed. The costs of merging as-is are different: one silent cross-version corruption path behind a default-off flag (#2181, two-constant fix), and two silent yield cliffs (#2180) that will read as "capture stopped producing samples" after a rolling upgrade or under compaction. Fix the first; decide the second two on purpose; then merge in stack order.
