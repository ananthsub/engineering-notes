External token staging: integrity fixes landed, but integration contracts remain open

A cross-repository review of Gym #2872, its token-capture ancestry, and the active NeMo RL #3837 integration through TransferQueue and SingleController.

Verdict: the reproduced integrity and write-serialization defects are fixed, but the public integration contract is not settled. The current Gym head passes its hosted checks. The expanded review found unresolved boundaries in vLLM response normalization, streaming, terminal-call declaration, rollout identity, harness routing, prefix ownership, and the external ledger protocol. The core verifier is now shared and complete. The remaining questions determine whether an out-of-tree framework or a blackbox harness can implement the feature from Gym’s public interfaces without copying RL- or OpenHands-specific behavior.

What changed: tokens move once, custody metadata moves end to end

The original Gym capture path keeps complete token records in Gym-owned storage. The external-staging mode splits that responsibility. The inference worker owns the exact token delta and writes it to a framework-provided sink. Gym admits each call, records a token-free custody row, attributes a terminal call, and seals a receipt. The training framework fetches the staged deltas and verifies that the receipt, snapshots, parent graph, chained hashes, and terminal whole-sequence hash all agree.

One two-call rollout

call A (text root)
  prompt IDs       [10, 20]
  generated IDs    [30]
  staged delta     [10, 20, 30]   mask [0, 0, 1]
  custody row      key=A, parent=None, prev=0, delta=3, cumulative=3

call B (continues A)
  authorized prefix [10, 20, 30]
  generated IDs     [40, 50]
  staged delta      [40, 50]      mask [1, 1]
  custody row       key=B, parent=A, prev=3, delta=2, cumulative=5

sealed terminal B → verified training row
  token IDs         [10, 20, 30, 40, 50]
  token mask        [0,  0,  1,  1,  1]

TransferQueue stores the two staged deltas. Gym’s ledger stores the keys, lengths, parent edge, versions, and hashes but not these token arrays. The finalizer follows B → A, reverses that ancestry, and accepts the five-token row only when the staged bytes reproduce the ledger’s link hashes and B’s whole-sequence hash.

Correct ownership direction

The heavy arrays stay next to the trainer’s data plane. Gym no longer has to relay training tokens through the agent/environment path.

Fail-closed call lifecycle

A staging failure returns capture_failed coordinates rather than pretending custody succeeded. Capture failure does not fail the model completion itself.

Integrity has two layers

Per-link chain hashes establish ordered ancestry. A terminal cumulative hash anchors the rebuilt whole sequence and catches a chain that is internally self-consistent but not the sequence the worker claimed.

Legacy behavior remains opt-in safe

External staging is a server configuration mode. The complete-record capture path remains the default and is not replaced.

Stack and compatibility boundary

Two related Gym changes now define important boundaries around #2872. #2783 makes one UUID rollout identity mandatory and independent of capture. After that change, #2872 should consume the shared ng_rollout_id rather than introduce a separate optional capture_rollout_id. #2823 supplies Megatron prefixes inline, while the vLLM integration reconstructs prefixes from externally staged records. The adapter contract must support both without making each engine reproduce storage-specific logic.

Not blockingThe RL pin carries the Gym fix that ultimately landed

The original review treated RL’s synthetic Gym commit 8e983c571ff09e8f20c45bcf7f501469854d54fa as a release blocker. That was too strong. The strict-tool fix is in Gym’s current branch at the vLLM dispatch boundary. RL currently pins public Gym commit b09d85fc8a3ad55eda7c33aef888b2277028d891; the PR-specific token-capture files are identical to rebased Gym head 805de0b7a00548edcade39ce7765c2c9300f6838.

Assessment. Final repinning remains routine integration hygiene, not a release blocker for #2872.

Correctness findings

Fixed after reviewDeferred routed-expert finalization now uses Gym’s complete integrity verifier

The original RL deferred path maintained a second linearizer and accepted a malformed terminal cumulative hash that Gym rejected. Gym now separates the base staged snapshot from deferred extras. Its verify_and_linearize compares every receipt field, recomputes staged digests, validates the graph, re-derives every chain hash, checks the terminal cumulative hash, and returns ordered ExtrasCommitment values without fetching route bytes.

RL head 64fe13987a47042b979f2adf065cf92addadd5c0 calls that verifier for both modes and constructs its route plan only afterward. See the unified finalizer flow and point-of-use extras verification.

same malformed receipt, same staged token deltas

  valid = false
  reason = rebuild_failed:cumulative_hash_mismatch

old deferred path:
  valid = true
  tokens = [10, 20, 30]

updated direct and deferred paths:
  valid = false
  reason = rebuild_failed:cumulative_hash_mismatch

Assessment. The performance mode no longer changes the custody checks. Route bytes remain deferred, but their digest commitments are bound into the already-verified staged records and checked when the policy consumes them.

Fixed after reviewCheckpoint restore had broken replay-buffer parallel-array invariants

TQReplayBuffer.reserve appends to all parallel arrays, including _rollout_ids_list and _staging_keys_list. remove indexes the staging-key list, and _delete_slot deletes from both. But load_state_dict restores only the older arrays and group IDs.

after restoring one ready group:
  len(meta_list)          = 1
  len(_rollout_ids_list)  = 0
  len(_staging_keys_list) = 0

await remove([0], remove_in_dp=False)
  IndexError: list index out of range

Original impact. A resumed run could fail as soon as the train pump consumed or evicted a restored group.

Current status. RL head 14dde627ad62426beeeddb148b5f089595adb022 now appends both capture bookkeeping entries during restore. The implementation records None because restored groups are already finalized and own no staged rows. See the repaired restore loop.

ConfirmedMixed weight versions reject as configured

A focused check with a terminal chain spanning versions 1 and 99 produced mixed_weight_versions:1..99 under the reject policy. The implementation computes min/max across the manifest after rebuild. This is conservative and prevents mixed-policy trajectories from entering training when rejection is requested.

ConfirmedThe main verifier has the right invariant ordering

The canonical path validates schema versions and poison state before reading semantics, requires a one-to-one ordered snapshot set, compares every custody field, recomputes digest inputs, validates the full manifest graph, selects only terminal ancestry, derives chain hashes in order, and finally checks the terminal whole-sequence anchor. This is a strong fail-closed design, and the terminal-only cumulative hash avoids quadratic rehashing.

Planned follow-upFingerprint the response representation that the client receives

The vLLM path can move parsed reasoning back into <think> text before recording output and continuation fingerprints. The later Responses conversion can extract that text into a standalone reasoning item. Gym’s assistant_fingerprint deliberately ignores standalone reasoning. The stored fingerprint can therefore describe the internal chat payload rather than the Responses payload returned to the harness.

Recommended follow-up. Normalize the vLLM completion into the final served Responses representation before computing fingerprints. This preserves the rule that terminal attribution hashes what the client can later return.

Contract gapSWE names a terminal response, but Gym’s built-in finalizer ignores it

SWE stores the selected session’s final response.id in a field named terminal_logical_request_id. RL #3837 uses that value as a declared response ID. Gym’s built-in consumer passes only an explicit model-call ID to resolve_terminal. The same SWE result can therefore select its terminal call under RL external staging but fall back to content or branch inference under Gym reconstruction.

Requested change. Rename the field to terminal_response_id and pass it through the shared consumer, or document that it is an external-finalizer-only contract.

Planned follow-upExternal capture rejects the streaming paths used by blackbox CLIs

_reject_external_capture_streaming prevents a capture-enabled streaming request from reaching the worker. Codex and Claude Code use streaming model APIs. Their rollout-prefixed base URLs can route correctly, but external staging still cannot capture those calls.

Recommended follow-up. Validate Gym’s existing buffer-then-replay stream handling with external worker commits, then add streaming support without delaying the first non-streaming version.

Performance implications

Fixed after reviewUnrelated staging writes now overlap

Gym’s complete_call now locks only the per-call single-completion transition. It invokes StagingSink.stage after releasing that lock, while still waiting for durability before returning commit coordinates. The sink protocol explicitly requires thread-safe implementations.

synthetic sink latency: 50 ms
four calls before: ~206 ms
four calls after:   ~55 ms

Assessment. This removes worker-wide head-of-line blocking without weakening single-shot completion or parent-before-child causality. A child cannot be admitted from its parent until the parent’s stage call has returned and Gym has recorded its coordinates.

Out-of-tree adapters and code reuse

The intended seam remains small: Gym does not import TransferQueue, and the framework supplies storage plus engine-specific extraction. The current public interfaces do not yet express the behavior used by the first integration. Two gaps matter for an independent implementation.

Good: storage inversion

An external framework implements stage and fetch without modifying Gym. Opaque staging keys keep the custody ledger storage-neutral.

Gap: the ledger signature does not match its caller

CaptureLedger.record declares only staging_chain beyond its base arguments. The vLLM call passes many more metadata keywords. Runtime protocol checks confirm only that the method exists, so an implementation can pass startup validation and fail on its first completion. One validated CaptureLedgerCommit object is more sustainable than a growing keyword list.

Gap: prefix resolution bypasses the adapter

CaptureAdapter.enter_prefix has no caller in RolloutTokenCapture. RL’s vLLM worker fetches and concatenates staging_chain records itself. The framework worker should resolve inline or staged prefixes to exact IDs and then always call the adapter.

Constraint: synchronous boundary

Adapters and sinks are synchronous. Async serving hosts must move blocking storage calls off their event loop. The sink must allow unrelated writes to overlap.

One prefix contract can serve Megatron and vLLM

Megatron admission
  required_prefix_token_ids = [10, 20, 30]
  staging_chain             = []

vLLM admission
  required_prefix_token_ids = []
  staging_chain             = ["call-A"]

framework worker resolves either form
  prefix_ids = [10, 20, 30]

engine adapter receives one input
  adapter.enter_prefix(request, prefix_ids)

The framework worker owns access to its staging source. The adapter owns only the engine request format. That boundary keeps Megatron’s inline prefix fast, lets vLLM fetch from TransferQueue, and prevents each out-of-tree engine from learning both storage representations.

Out-of-process harnesses need a routing contract, not one patch per harness

Existing capture and external capture both depend on a rollout-prefixed model URL. OpenHands additionally receives a sitecustomize.py monkeypatch, even though the PR also writes the prefixed URL into its LLM configuration. No test executes the monkeypatch or demonstrates the request path that loses the configured prefix. Codex, Claude Code, and OpenCode can receive a provider base URL directly. A supported harness contract should require every model call, retry, and subagent call to preserve the prefix and return enough information to identify the terminal call. A local proxy is a more general fallback for clients that rewrite URLs.

Code understandability

Gym’s new package is easiest to understand as four layers: wire records, digest functions, one worker lifecycle, and one verifier. The implementation follows that split, but several names and comments describe design arguments rather than observable behavior. “Metadata-only” means extras-free, not token-free. StagedCallBaseSnapshot still carries token IDs, masks, and logprobs. terminal_logical_request_id contains a response envelope ID, while the separate x-nemo-gym-logical-request-id header has no in-repository sender and no downstream use after the model middleware copies it into a ledger row.

LineageStore is the read-only parent resolver used beside the original TokenSink. CaptureLedger adds successful-call writes, failure writes, and manifest reads for external staging. That interface split is reasonable, but callers remain typed as LineageStore while invoking ledger-only methods. Renaming the base interface to LineageResolver and narrowing external paths to CaptureLedger would make the ownership visible.

Recommended cleanup. Describe concrete reads, writes, IDs, and failure behavior instead of “custody,” “witness,” “poison,” and “seal” terminology. Rename values to match their contents. Return typed objects at public extension boundaries. Update the PR body to describe the extras-free verifier and deferred route flow that the code now implements.

Validation evidence and limits

The review pinned the rebased public heads, compared the RL-pinned Gym revision against #2872, inspected the custody and TQ boundaries, and reran focused dependency-light checks. The update preserves every base-row integrity check, removes RL’s alternate linearizer, and makes unrelated sink calls concurrent. The lock comparison used four concurrent calls and a deterministic 50 ms sink.

  1. Can CaptureLedger.record accept one validated commit object whose fields match the actual vLLM call?
  2. Will the framework worker resolve both inline and staged prefixes before calling CaptureAdapter.enter_prefix?
  3. Can #2872 consume the mandatory rollout identity from #2783 instead of adding optional capture_rollout_id, ng_rollout_id, and capture-mode values in several request and harness objects?
  4. Why is the OpenHands monkeypatch needed when existing capture and external capture both use a configured rollout-prefixed base URL? Which executed test proves that the configured URL is lost?
  5. Will the vLLM path fingerprint the final served Responses representation and scope envelope-ID preservation to the active captured request?
  6. Will SWE expose a consistently named terminal response ID to both Gym and RL finalizers?
  7. Are x-nemo-gym-logical-request-id and x-nemo-gym-capture-capability part of a real end-to-end protocol? The first has no sender and its recorded value is not read. The second is sent but not validated or bound to the rollout path.
  8. Can the unconsumed HttpByteCounterMiddleware be removed from the production server path?
  9. Which public end-to-end test demonstrates external staging through final policy consumption, including a later streaming and blackbox-harness follow-up?
Suggested integration gate. Stabilize the public ledger, prefix, identity, terminal-ID, and harness-routing contracts before treating this as an out-of-tree extension point.
