Public code review · snapshot 31 August 2026

External token staging: the contract is strong, the integration still has two correctness gaps

A cross-repository review of Gym #2872, its token-capture ancestry, and the active NeMo RL #3837 integration through TransferQueue and SingleController.

Verdict: request changes on the current integration path. Gym #2872 introduces a carefully separated, fail-closed custody protocol and materially reuses the existing token-capture lineage and terminal-attribution machinery. The out-of-tree seam is credible. But RL #3837 has two reproducible correctness defects: deferred routed-expert finalization bypasses Gym’s terminal cumulative-hash check, and checkpoint restore leaves new replay-buffer ownership arrays empty, causing removal after restore to fail. The worker capture lock also serializes every synchronous staging write. Finally, RL validates against a synthetic Gym revision rather than the current #2872 head, so the pair is not yet one reproducible source contract.

What changed: tokens move once, custody metadata moves end to end

The original Gym capture path keeps complete token records in Gym-owned storage. The external-staging mode splits that responsibility. The inference worker owns the exact token delta and writes it to a framework-provided sink. Gym admits each call, records a token-free custody row, attributes a terminal call, and seals a receipt. The training framework fetches the staged deltas and verifies that the receipt, snapshots, parent graph, chained hashes, and terminal whole-sequence hash all agree.

One two-call rollout

call A (text root)
  prompt IDs       [10, 20]
  generated IDs    [30]
  staged delta     [10, 20, 30]   mask [0, 0, 1]
  custody row      key=A, parent=None, prev=0, delta=3, cumulative=3

call B (continues A)
  authorized prefix [10, 20, 30]
  generated IDs     [40, 50]
  staged delta      [40, 50]      mask [1, 1]
  custody row       key=B, parent=A, prev=3, delta=2, cumulative=5

sealed terminal B → verified training row
  token IDs         [10, 20, 30, 40, 50]
  token mask        [0,  0,  1,  1,  1]

TransferQueue stores the two staged deltas. Gym’s ledger stores the keys, lengths, parent edge, versions, and hashes but not these token arrays. The finalizer follows B → A, reverses that ancestry, and accepts the five-token row only when the staged bytes reproduce the ledger’s link hashes and B’s whole-sequence hash.

Correct ownership direction

The heavy arrays stay next to the trainer’s data plane. Gym no longer has to relay training tokens through the agent/environment path.

Fail-closed call lifecycle

A staging failure returns capture_failed coordinates rather than pretending custody succeeded. Capture failure does not fail the model completion itself.

Integrity has two layers

Per-link chain hashes establish ordered ancestry. A terminal cumulative hash anchors the rebuilt whole sequence and catches a chain that is internally self-consistent but not the sequence the worker claimed.

Legacy behavior remains opt-in safe

External staging is a server configuration mode. The complete-record capture path remains the default and is not replaced.

Stack and compatibility boundary

Release blockerRL does not pin the current Gym PR head

RL #3837 pins Gym commit 8e983c571ff09e8f20c45bcf7f501469854d54fa. Its own commit message describes that revision as the earlier #2872 tree plus a separately cherry-picked strict-tool stripping fix. The current Gym #2872 head is c5dccdb6125e2931da0a01c26417b38493e76556. A direct diff is non-empty: the current head narrows SWE-agent integration and differs in response-converter behavior.

Impact. The compatibility PR is not validating the exact code proposed by #2872. A merge or later rebase can silently select one side of the bespoke combination. Put the required strict-tool fix and narrowing changes in #2872, then pin #3837 to that exact public head and rerun the cross-repository tests.

Correctness findings

HighDeferred routed-expert finalization omits the terminal cumulative-hash check

Gym’s canonical verifier recomputes every staged digest, validates the manifest graph, re-derives the chain hash for each link, then compares the rebuilt terminal sequence with cumulative_hash. See the canonical verifier, especially its chain and terminal checks.

RL’s deferred-route mode instead calls its own _linearize_metadata_only. That copy validates graph shape and mask order, but it does not recompute chain hashes, does not check the terminal cumulative hash, and does not reject an empty training row. The dispatch between the two paths is visible in finalize_rollout.

same malformed receipt, same staged token deltas

standard path:
  valid = false
  reason = rebuild_failed:cumulative_hash_mismatch

deferred routed-expert path:
  valid = true
  tokens = [10, 20, 30]

Impact. Enabling the performance optimization weakens the custody contract and can accept a sequence the terminal worker hash does not authorize. This is a security-like integrity boundary even if the expected failure source is accidental corruption.

Fix. Do not maintain a second linearizer. Extend Gym’s verifier with an option or callback that verifies extras metadata without materializing route bytes, while preserving all common receipt, digest, graph, chain, terminal, and mask invariants. Add one parametrized corruption suite that must produce identical accept/reject results in direct and deferred modes.

HighCheckpoint restore breaks replay-buffer parallel-array invariants

TQReplayBuffer.reserve appends to all parallel arrays, including _rollout_ids_list and _staging_keys_list. remove indexes the staging-key list, and _delete_slot deletes from both. But load_state_dict restores only the older arrays and group IDs.

after restoring one ready group:
  len(meta_list)          = 1
  len(_rollout_ids_list)  = 0
  len(_staging_keys_list) = 0

await remove([0], remove_in_dp=False)
  IndexError: list index out of range

Impact. A resumed run can fail as soon as the train pump consumes or evicts a restored group. Staging ownership is also absent from the serialized checkpoint, so simply appending None would prevent the crash but would not preserve deferred-route cleanup responsibility.

Fix. Add rollout IDs and staging keys to the checkpoint schema, validate them during preflight, restore every parallel array atomically, and test save → load → consume as well as save → load → stale eviction in capture mode. If old checkpoints are supported, define an explicit migration policy for missing ownership fields.

ConfirmedMixed weight versions reject as configured

A focused check with a terminal chain spanning versions 1 and 99 produced mixed_weight_versions:1..99 under the reject policy. The implementation computes min/max across the manifest after rebuild. This is conservative and prevents mixed-policy trajectories from entering training when rejection is requested.

ConfirmedThe main verifier has the right invariant ordering

The canonical path validates schema versions and poison state before reading semantics, requires a one-to-one ordered snapshot set, compares every custody field, recomputes digest inputs, validates the full manifest graph, selects only terminal ancestry, derives chain hashes in order, and finally checks the terminal whole-sequence anchor. This is a strong fail-closed design, and the terminal-only cumulative hash avoids quadratic rehashing.

Performance implications

MediumOne worker capture object serializes every staging write

Gym’s complete_call holds the same threading.Lock while calling the external StagingSink.stage. RL’s TQ sink is synchronous and waits for a data-plane acknowledgement, so lock hold time includes tensor construction, TransferQueue submission, and network/actor latency.

synthetic sink latency: 50 ms
four concurrent complete_call operations: ~207 ms
expected if independent: ~50–60 ms
observed behavior: approximately 4× serialization

Impact. If a serving worker handles concurrent requests, staging throughput is capped at one write per worker. Tail latency from a slow TQ write blocks unrelated rollouts. The protocol already says blocking implementations must be moved off an event loop, but it does not say that all calls will be globally serialized.

Fix choices. Make sink thread safety part of the protocol and keep the lock only around the single-shot completion claim; or use keyed/per-rollout synchronization if the sink needs ordering only within a rollout. Benchmark with realistic TQ actor latency and concurrent engine requests before choosing.

Out-of-tree adapters and code reuse

The core seam is deliberately small. StagingSink, StagingSource, WeightVersionProvider, and CaptureAdapter use Python protocols and plain records. Gym does not import TransferQueue. The adapter owns only engine extraction and prefix attachment; the capture object owns admission, lifecycle, normalization, hashing, staging, and failure coordinates.

Good: storage inversion

An external framework implements stage and fetch without modifying Gym. Opaque staging keys keep the custody ledger storage-neutral.

Good: engine inversion

A non-vLLM engine can implement four extraction methods while inheriting the same digest and lifecycle semantics.

Constraint: synchronous boundary

Adapters and sinks are intentionally synchronous. Async serving hosts must explicitly move blocking work off their event loop, and concurrency semantics should be documented.

Constraint: install shape

The serving layer must expose install_token_capture(capture). That is small, but an out-of-tree implementation still needs a host shim.

Code understandability

Gym’s new package is easiest to understand as four layers: immutable wire records, canonical digest functions, one worker lifecycle, and one verifier. That separation is effective. The names CaptureAdmission, StagedCallRecord, CommitCoords, RolloutManifest, and RolloutReceipt describe the custody transition clearly.

The cross-repository system is harder to reason about because state is represented in several parallel forms: Gym ledger records, TQ staging rows, finalizer requests, canonical TQ rows, replay-buffer slots, and optional route plans. The PR descriptions are unusually thorough, but correctness should not depend on readers keeping duplicate algorithms and parallel arrays mentally synchronized.

Recommended simplification. Treat Gym’s verify_and_linearize as the only accept/reject authority. Expose a verified chain plan containing token spans and digest-checked extras references. RL can then choose direct or deferred route materialization after verification without reimplementing custody semantics. Separately, replace replay-buffer parallel arrays with one slot dataclass so save, load, reserve, commit, and remove operate on the same state object.

Validation evidence and limits

The review pinned public heads, compared the RL-pinned Gym revision against #2872, inspected the custody and TQ boundaries, and ran focused dependency-light reproductions for each behavioral claim. The two high-severity failures were reproduced directly against the reviewed revisions. The lock result used four concurrent calls and a deterministic 50 ms sink.

Questions to resolve before merge

  1. Can deferred routed-expert mode call one Gym-owned verifier and receive a verified route-span plan, eliminating _linearize_metadata_only?
  2. What is the checkpoint contract for staging ownership? Must deferred route fragments survive restart until policy consumption, and how are older checkpoints migrated?
  3. Is StagingSink.stage required to be thread-safe? If not, what ordering guarantee requires a worker-global lock rather than rollout-scoped synchronization?
  4. Which exact Gym commit is intended to merge with RL #3837? Can #2872 absorb the strict-tool fix so the compatibility PR pins the public head rather than a synthetic commit?
  5. Which end-to-end test exercises save → restart → restored group consumption with token capture and deferred routed experts enabled together?
Suggested merge gate. Fix and regression-test both high-severity defects, align the Gym pin exactly, and publish one end-to-end SingleController run that enables external staging, checkpoint/resume, and deferred routed experts. The lock can be a documented follow-up only if measured TQ concurrency shows it is not on the critical throughput path.
