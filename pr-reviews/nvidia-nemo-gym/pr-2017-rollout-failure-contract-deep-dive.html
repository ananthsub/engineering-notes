PR #2017 fixes evaluation failure routing, not the shared training contract

Reviewed: Gym PR #2017 at 62df56df4cd4e2edc1ee28e083a09c75cf2fbccf, against Gym issue #2750. Training comparison: NeMo-RL 6ae035784fe40fd9c9e31d27fffa4a403243a0bd, which pins Gym c3bac96314a59f28b896f597eb9845d175bb0252.

Answer: the PR is the right shape for managed evaluation. A failed agent call becomes a row-associated sidecar record with no invented reward, unrelated rows continue, and evaluation chooses whether selected classes count as zero. It intentionally leaves NeMo-RL on the old exception interface. NeMo-RL then applies its own row and prompt-group retry policy, without receiving the failure class that evaluation sees. Its two rollout paths also disagree on whether Gym’s mask_sample prevents training. That boundary preserves compatibility, but it is not yet the common contract proposed by issue #2750.

Evaluation gains a failure value where it used to get an exception

Before the PR

run_from_config() awaits each future before it can route a result. If POST /run, status handling, body reading, or JSON decoding raises, collection exits at that await. Earlier completed rows remain on disk, but the failed input has no row-associated record.

At PR head

Managed collection calls run_examples(..., route_failures_to_sidecar=True). Expected request failures become plain dictionaries. The loop stamps the input row’s task, rollout, attempt, and agent identity before writing the record to the failure sidecar.

The important constraint is absence: an agent_run_error or agent_request_failed contains neither reward nor response. It therefore cannot look like a verifier score or a trainable generation. See the failure-row builder and the persistence loop.

Scoring remains a separate decision. The default denominator contains only completed rollouts. count_failure_classes_as_zero can project selected sidecar records into the aggregation request with reward: 0.0, without changing either stored artifact. That matches issue #2750’s rule that infrastructure is not silently turned into verifier output.

The agent endpoint returns HTTP 500

Managed evaluation writes agent_run_error with status, exception type, message, and a bounded body. It does not resend that HTTP response in place. Resume can later create a new rollout attempt. The PR assumes a NeMo Gym agent itself uses 500 when its handler raises.

{
  "_ng_task_index": 7,
  "_ng_rollout_index": 2,
  "_ng_attempt_index": 0,
  "_ng_failure_class": "agent_run_error",
  "_ng_failure_http_status": 500,
  "_ng_failure_type": "ClientResponseError"
  // no reward, response, or token sequence
}

A gateway returns HTTP 503

The same row becomes agent_request_failed. This label says the reply does not prove that the agent ran. It is still a completed failure record for persistence, but not evidence about model quality.

The connection fails

The unit-level dispatcher can convert a surfaced ClientError into agent_request_failed. The production shared transport often prevents that branch from running: internal connection, disconnect, and timeout paths can retry without a finite default. The sidecar and resume limit apply only after the lower request call returns or raises.

Resume creates another attempt

The first resume sends the same task and rollout with _ng_attempt_index: 1. Under the default maximum of three rollout attempts, later resumes stop dispatching after three recorded sidecar attempts. A later success suppresses earlier failures when online aggregation builds its scored set. See resume accounting.

NeMo-RL needs a complete group, so it treats “no result” as control flow

Current NeMo-RL does not call the managed CLI path. A Ray actor starts Gym services, creates RolloutCollectionHelper, and calls the lower-level run_examples() interface with its default failure routing disabled. The actor then converts each Gym Responses record into training messages.

  1. NemoGym._spinup() starts Gym and points its model server at NeMo-RL’s exposed generation endpoints.
  2. AsyncNemoGymRolloutImpl._build_inputs() clones one prompt into the configured group size and stamps each row with _rowidx.
  3. NemoGym.run_rollouts() streams Gym futures in completion order. One exception terminates that actor stream.
  4. Postprocessing accepts only output items with generation token IDs and requires prompt IDs and generation log probabilities. If none remain, it raises “no generation data.”
  5. SingleController collection retains arrived slots and re-dispatches only missing row indices. It emits a prompt group only after every slot is filled.
  6. GRPO advantage estimation computes a group-relative baseline across all responses for the prompt.

NeMo-RL’s exception policy is richer than fail-fast, but separate from Gym’s labels

Before crossing the Ray boundary, HTTP errors become picklable NeMo-RL exceptions. Every 5xx, 408, and 429 becomes GymTransportError; other statuses become RolloutDataFailure. A status-less exception is re-raised unchanged. SingleController defaults to three missing-row attempts, five infrastructure attempts per prompt, and two data attempts. Exhausted prompts stop the run by default; optional drop, shrink, or replacement policies are configured above this layer.

This means an HTTP 500 has two names in the same end-to-end system: managed Gym calls it agent_run_error, while NeMo-RL calls it infrastructure. PR #2017 does not pass its classification to NeMo-RL, so the trainer cannot choose policy from the same evidence evaluation uses.

A complete but unusable result follows a different path

NeMo-RL’s legacy batched path reads full_result.instance_config.mask_sample. The sample remains in reward and group-baseline calculations, then its training loss multiplier is set to zero.

SingleController preserves the flag only in Completion.env_extras. DataPlane payload construction ignores those extras and creates an all-ones sample_mask, so the flagged sample trains normally. failure_kind and failure_reason have no training consumer at this revision.

PR #2017 implements one layer of issue #2750

The proposed design at public design revision 354bd2f4… separates transport safety from caller policy. Gym should decide whether another HTTP transmission is safe. After Gym returns a success or structured failure, evaluation or training decides whether to retry the rollout, replace it, keep and mask it, drop it, or stop.

Six reproduced findings should shape this review

1. The lower transport can retry forever and replay POST /run

The shared request loop keeps internal timeout, disconnect, and ClientOSError branches alive without a finite default. ServerClient marks the request internal, and run_examples() supplies no connection-retry bound.

A persistent timeout was observed continuing beyond three attempts. If the agent performed work before the connection dropped, each transport retry can duplicate that work. The new failure row never appears because control does not return to the PR’s catch block.

Requested direction: give /run a finite, shared retry allowance and an explicit replay policy. A possibly delivered POST should return a failure outcome instead of being transmitted again.

2. Offline shard aggregation can suppress another shard’s failure

_failure_rows_counted_as_zero() and offline aggregation use only (task_index, rollout_index) as global identity across every shard.

shard A main:     (task=0, rollout=0, reward=1)
shard B sidecar:  (task=0, rollout=0, agent_run_error)

expected metric input: [1, 0]  → mean 0.5
observed metric input: [1]     → mean 1.0

Requested direction: include shard/run provenance or a globally unique rollout identifier in success suppression and failure deduplication. Add a regression with two shards that reuse local indices.

3. A stale selected failure can outvote the latest attempt

The same helper checks whether a row’s class is selected before it updates the per-rollout map. An earlier selected agent_run_error therefore survives when a later attempt is agent_request_failed and only the first class is selected.

attempt 0: agent_run_error       ← selected
attempt 1: agent_request_failed  ← latest, not selected
observed: attempt 0 still contributes reward 0

This contradicts the helper’s “last attempt wins” contract and changes both denominator and prompt-group size. Existing duplicate coverage uses the same class on both attempts, so it cannot detect the transition.

Requested direction: deduplicate all attempts first, then filter the latest record by class. Add a selected-to-unselected transition test.

4. One direct-caller exception leaves sibling requests running during retry

as_completed schedules every row. When NeMo-RL propagates the first failed future, neither side cancels and drains the remaining Gym tasks before missing rows are redispatched.

The reproduction observed two simultaneous requests and two successful completions for each still-running sibling. For stateful agents, that can duplicate model calls, tools, sandbox mutations, remote sessions, cost, and load.

Requested direction: make the stream own its scheduled tasks and cancel/drain them before exposing a terminal exception, or provide explicit attempt identity and receiver-side deduplication before the caller redispatches.

5. HTTP status alone cannot prove that the agent ran

The classification treats every status outside {429, 502, 503, 504} as agent_run_error. The probe confirmed that 500 enters this potentially scoreable class while 502 becomes agent_request_failed.

HTTP status does not identify which hop generated a response. A configured endpoint can terminate at a proxy or service mesh. If that intermediary returns 500 before forwarding, opting agent_run_error into zero scoring converts an infrastructure failure into a model zero. The tests lock in the status-only assumption rather than proving the response’s origin.

Requested direction: establish origin with a trusted agent error envelope or another explicit signal. Treat an origin-unknown 500 as infrastructure rather than as evidence that the model ran.

6. SingleController drops Gym’s training mask

Consider two complete responses with rewards [0.0, 1.0]. The first carries mask_sample=true, failure_kind, and failure_reason. The reproduced paths disagree:

legacy GRPO loss mask:      [0.0, 1.0]
SingleController sample_mask: [1.0, 1.0]
SingleController LOO baseline: [1.0, 0.0]
SingleController advantage:    [-1.0, 1.0]

Legacy extraction adds the flag to the final batch, and GRPO converts it into the policy sample_mask. Both legacy baseline calculation and the shared estimator deliberately use all rewards, so the masked sample still changes its peers’ advantages.

SingleController forwards the configuration gate but carries the row flag only as completion metadata. The DataPlane payload does not translate it into sample_mask. Repository-wide tracked-source search also found no consumer of failure_kind or failure_reason.

Requested direction: propagate Gym’s mask from Completion.env_extras into the DataPlane sample_mask, and add an end-to-end SingleController regression. Decide separately and document whether a loss-masked reward should remain in the prompt-group baseline.

Two code-backed questions remain outside the reproduced findings

Should resume validate the run before consuming old attempts?

Resume trusts the prior materialized input and matches only task and rollout indices. Reusing an output path after changing prompts, routing, or generation configuration can dispatch stale rows and spend the new run’s retry budget on old failures. Issue #2750 calls for input and resolved-config digests before reuse.

When does NeMo-RL receive the common failure vocabulary?

The direct interface preserves raw exceptions, and NeMo-RL converts HTTP status into its own two-class taxonomy. The conversion drops Gym’s proposed failure_kind, stage, delivery state, endpoint, and bounded response body. Should this PR expose a serializable structured outcome now, or explicitly depend on the later run_outcomes() contract before training policy is considered covered?

Reviewer consequence

Review PR #2017 as the managed-evaluation layer of issue #2750, not as the end-to-end rollout failure contract. Its central decision—store no-result failures separately and never invent generation data—is sound and compatible with NeMo-RL. The aggregation identity bugs, uncancelled direct-caller work, and status-only origin inference are concrete correctness issues in this patch’s paths. SingleController’s dropped mask demonstrates that “return a complete masked result” is not yet a caller-independent NeMo-RL policy. The lower retry loop, shared structured outcome, replay identity, cleanup, and unified training-mask contract still need explicit ownership before evaluation and training can claim the same failure semantics.
