How sandbox filesystem snapshots support rollout checkpointing

PR #2636 gives a rollout coordinator a way to commit an OpenSandbox root filesystem, release its runtime, hand the stable sandbox ID to another process, recreate an exec-ready runtime from that filesystem, and clean up records left by interrupted runs. This page traces that path and compares it with the later, broader contract proposed by issue #3024.

PR head: 03b229fec7ca… PR comparison base: d23a85ac7d31… Target main observed at 2448579496dc… Reviewed 2026-09-10 UTC
Short answer: PR #2636 implements a filesystem-preservation primitive, not a live-runtime checkpoint or the rollout checkpoint transaction. OpenSandbox commits the root filesystem as an OCI image, releases the Pod and its processes, keeps the sandbox ID stable, then creates a new runtime from the image on resume. Process memory, sockets, and PTY processes do not survive. Issue #3024 still needs a coordinator to bind this filesystem state to matching agent, resources, model-lineage, token-store, rollout-ID, and attempt state. Two independently reproduced gaps remain: the configured timeout does not bound the complete resume call, and moving pagination can leave a snapshot behind while cleanup returns success.

Before · d23a85ac7d31…

No provider-neutral pause contract

AsyncSandbox and Sandbox had no pause() or resume(). A provider status of paused mapped to UNKNOWN. Reconnecting always health-checked the exec daemon unless the caller disabled checks globally, but a paused sandbox has no live exec daemon to probe.

hasattr(AsyncSandbox, "pause")  # False
_to_sandbox_status("paused")   # UNKNOWN
After · 03b229fec7ca…

Optional capability with a paused state

The public API detects SupportsSandboxPauseResume structurally. OpenSandbox maps paused to PAUSED, accepts a paused descriptor without an exec-daemon probe, and makes resume() responsible for creating a new runtime from the committed root filesystem and returning a fresh SDK handle.

hasattr(AsyncSandbox, "pause")  # True
_to_sandbox_status("paused")   # PAUSED

Public API: async pause/resume and sync wrappers · Capability and state: SandboxStatus and SupportsSandboxPauseResume.

Worked checkpoint: preserve sb-42's files between two processes

Assume rollout rollout-42 is executing inside OpenSandbox sb-42. Its working directory is /workspace, its provider-owned SDK object is raw-A, and process A has PTY client pty-7. The root filesystem and sandbox ID survive. The running command, memory, sockets, and PTY process do not.

Four responsibilities make the handoff work

Public contract

Capability detection keeps other providers honest

Pause/resume is optional. Providers that do not implement both methods fail with NotImplementedError instead of inheriting a false preservation guarantee.

facade dispatch · unsupported-provider regression

Status contract

Paused becomes a first-class provider-neutral state

OpenSandbox's paused state maps to SandboxStatus.PAUSED. Transitional pausing and resuming states remain STARTING, which tells callers that the runtime is not ready yet.

status normalization

Deadline contract

Pause has one end-to-end budget

The outer asyncio.timeout includes both the mutating pause request and all status polls. The pause request is not retried because a connection failure leaves its outcome unknown. A shorter request timeout is preserved inside the longer lifecycle budget.

pause deadline · deadline regressions

Ownership contract

The provider-neutral handle survives; its raw client does not

Callers keep the same SandboxHandle. Resume closes the stale client and replaces handle.raw. Existing facade methods therefore route later exec, upload, download, endpoint, and status calls through the rebuilt SDK object.

in-place handle refresh · facade-level assertion

Reproduced finding · head 03b229fec7ca…

The configured lifecycle timeout does not bound a stalled resume request

Gym passes pause_resume_timeout_s to the SDK as resume_timeout, but does not put an outer deadline around Sandbox.resume(). The pinned SDK first sends the mutating resume request and resolves rebuilt exec and egress endpoints. It applies resume_timeout only when check_ready() begins.

PYTHONPATH=<PR-head-checkout> python -m pytest -q -s \
  test_resume_lifecycle_timeout.py

configured_lifecycle_timeout=0.05s
external_timeout_fired_after=0.12s
resume_call_cancelled_by=external_wait_for

1 passed in 0.19s

The reproduction stalled the SDK call before it returned. Gym exceeded the configured 0.05-second budget and stopped only when an independent 0.12-second timeout cancelled it. An outer asyncio.timeout(), matching the pause implementation, would bound the caller's wait. Because cancellation can leave the mutating request's server-side outcome unknown, the public contract should also say whether callers reconnect and inspect status before retrying.

unbounded Gym call · SDK request, endpoint rebuild, then bounded readiness · pause's outer-deadline analog.

Source-derived failure boundary: pause closes and forgets matching local PTY clients before sending the pause request. If that request times out or status polling ends in an error, Gym has no rollback path to reconstruct those clients or prove whether the server accepted the mutation. A caller must reconnect and inspect management state before deciding whether to resume, retry, or restart.

Pausing closes the local PTY object; the remote PTY process also ends

OpenSandbox PTYs are backed by local aiohttp and WebSocket clients. The PR records the owning sandbox ID on each session, then closes only sessions for the sandbox being paused. Gym suppresses its own PTY delete request, but OpenSandbox subsequently releases the runtime Pod. The remote PTY process and its memory are not part of the filesystem snapshot.

What closes

Process A's client, then the runtime

Gym sets session._owned = False before closing. That prevents close() from sending an explicit PTY DELETE. The closed client is removed from provider tracking. OpenSandbox pause then releases the Pod, so the remote process does not survive anyway.

What resume provides

A fresh runtime under the same sandbox ID

Resume recreates the runtime from committed files and rebuilds SDK endpoints. A caller that needs a terminal must create a new PTY session. The old session ID and replay offset cannot represent continuation of a process that no longer exists.

local PTY state · test proves only local target-scoped detachment · process and memory preservation limits.

Interrupted runs get an audit-first snapshot cleanup path

Pausing creates server-side snapshot records and OCI image tags. If the controlling process disappears, snapshot records and paused sandboxes remain. The new helper talks directly to the public management API and defaults to audit mode. Deletion requires --reap. Deleting a snapshot record does not delete its pushed OCI image; registry retention or garbage collection remains a separate operator responsibility.

python -m nemo_gym.sandbox.providers.opensandbox.snapshots \
  --connection-config opensandbox.yaml \
  --sandbox-id sb-42 \

Reproduced finding · head 03b229fec7ca…

One-pass numbered pagination can skip a shifted snapshot and still return success

The reproduction used a mocked page size of one. The same positional race applies at the production page size of 100. Page 1 returned snap-a and said another page existed. An external teardown then removed snap-a, shifting snap-b onto page 1. The helper requested page 2, saw nothing, treated the later delete of snap-a as an idempotent 404, and returned zero while snap-b remained.

PYTHONPATH=<PR-head-checkout> python -m pytest -q -s \
  test_snapshot_pagination_race.py

GET page=1 -> ['snap-a']
external delete removes snap-a
GET page=2 -> []
DELETE snap-a -> 404
exit=0 remaining=['snap-b']

1 passed in 0.09s

The neighboring cleanup helper documents this exact moving-page race and performs up to three list/delete sweeps. Snapshot cleanup should likewise re-list after deletion and return success only after an empty final inventory, or use a server-provided stable cursor if one exists.

one-pass numbered listing · single delete sweep and success return · bounded re-list analog · existing moving-page regression.

Failure ordering: snapshot deletion failures do not stop phase two. The helper records the failure, still deletes selected paused sandboxes, and returns a nonzero status afterward. Reviewers should decide whether best-effort teardown is intended or whether preserving a recoverable checkpoint should take precedence when its snapshot cleanup fails.
Operational boundary: selectors are optional. --reap without a sandbox, state, or snapshot selector targets every listed snapshot. Adding --kill-paused also targets every paused sandbox. Audit mode is safe, but the destructive form has deployment-wide scope rather than the run-and-user scope enforced by the older cleanup_sandboxes.py.

This is one lane of issue #3024, not a complete checkpoint

PR #2636 predates issue #3024 and is not part of the issue's listed prototype stack. The relationship is therefore an inference from their public contracts, not a declared dependency. The checkpoint proposal classifies blackbox runtime continuation as a later milestone that needs both runtime-provider snapshots and a checkpoint-aware egress relay. Its own out-of-scope section says that a filesystem-only sandbox snapshot is not automatically a complete opaque-agent runtime snapshot. PR #2636 supplies the filesystem snapshot lifecycle and stable sandbox identity. It does not add the egress relay or Gym's global prepare, commit, restore, resume, and stale-attempt protocol.

Concrete questions before treating this as rollout checkpointing

1. Which component binds sb-42 to the global checkpoint boundary?

The descriptor contains a sandbox ID and facade-added working directory. It does not carry checkpoint_id, rollout_id, attempt index, operation boundary, snapshot digest, resources revision, or model-call lineage. Issue #3024 assigns that consistency proof to an external coordinator and its aggregate manifest, not to the bare descriptor. A later integration test should pause at one completed agent boundary, commit all component manifests, restore as attempt N+1, and reject a global manifest whose runtime reference does not match the selected checkpoint.

descriptor contract · coordinator contract

2. How will a checkpoint prove that recent guest filesystem writes are durable?

OpenSandbox attempts sync inside each running container before committing the root filesystem, but failure only emits a warning and snapshotting continues. A successful PAUSED state can therefore coexist with missing recent writes. A checkpoint-aware agent should flush its own files and persist a boundary marker before pause, then validate that marker after resume. Otherwise the framework should classify the rollout for a fresh attempt rather than continuation.

best-effort guest sync · fail-closed checkpoint proposal

3. Should destructive snapshot cleanup require an explicit scope?

--reap with no selector deletes every snapshot returned by the deployment. --kill-paused additionally deletes every paused sandbox. More subtly, --snapshot-id snap-a --kill-paused --reap looks snapshot-scoped but still deletes every paused sandbox because exact snapshot IDs bypass listing while sandbox_id remains unset. The neighboring sandbox cleanup tool requires exact run and user metadata. Requiring a sandbox, run/user attribution, or explicit global-confirmation flag would make destructive scope visible. A CLI regression should cover the exact-ID plus --kill-paused combination.

unscoped inventory and reap · run/user-scoped analog

4. Will callers discard old PTY identity and create a new session after resume?

The pause path closes the caller's PTY object, and OpenSandbox recreates the runtime without process state. The cross-process descriptor correctly carries no PTY session ID or replay offset. A provider-backed regression should prove that old PTY identity is invalid after resume and that callers establish a new terminal process rather than attempting replay from a process that no longer exists.

local detachment · session replay state

5. Can the PR description match the final cleanup interface?

The public description still advertises list, delete, and cleanup subcommands with --dry-run. The reviewed head has no subcommands: it audits by default and deletes only with --reap. Updating the description would keep reviewers and operators from testing a superseded command shape.

current PR description · final argument parser

6. Where will users discover the preservation and failure contract?

The PR adds public sync and async methods but no Fern documentation. The user-facing contract needs to say that only root filesystem and template environment survive; processes, memory, sockets, and PTYs do not; guest sync is best-effort; pause and resume can have indeterminate outcomes after network failure; and resume currently has the reproduced timeout gap.

new public methods · actual preservation boundary

Practical consequence

  1. Review PR #2636 as a filesystem primitive: it creates a clean optional API, paused-aware reconnect, fresh-runtime handle replacement, and record cleanup. The pause deadline is complete; the resume deadline has the reproduced gap above.
  2. Do not advertise complete rollout checkpointing from this PR alone: no global boundary, manifest, attempt fence, checkpoint-aware egress relay, or cross-component restore order exists here.
  3. Make the next integration prove composition: one provider-backed failure test should stop at a completed operation boundary, flush and snapshot files, publish a consistent checkpoint, recreate execution in a new process, and continue without repeating the completed operation.
  4. Keep recovery fail-closed: if the filesystem snapshot cannot be reconciled with agent, resources, model, and token state, dispatch a fresh attempt or reject the checkpoint as issue #3024 requires.
