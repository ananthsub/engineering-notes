Partial-rollout checkpointing for NeMo Gym and NeMo RL

Design v2 on the environment-server architecture, with the v1 proposal preserved · draft for review

A long agentic rollout should survive a trainer checkpoint and a crash without being thrown away. This page walks through the lifecycle message by message: a normal episode, a checkpoint taken in place, a crash followed by a restore, a straggler that misses the deadline, and a generation that is cut mid-decode. Each step shows who sends what to whom and what every component's state machine is doing.

Part 1

The problem

Why checkpoint rollouts that are still running

Reinforcement-learning training periodically checkpoints the trainer so it can survive a crash or a preemption. Agentic rollouts make that hard: a multi-turn rollout with tool calls, a software-engineering task, or a long judged conversation can run for minutes or hours, and thousands run at once. There are two simple answers, and both fail at scale:

  • Restart every unfinished rollout after a crash. Every token already generated and every tool call already run is thrown away, and long rollouts may never finish between failures.
  • Wait for every rollout to finish before checkpointing. Checkpoint latency becomes the latency of the slowest rollout, and one hung tool call or harness blocks the checkpoint indefinitely.

Partial-rollout checkpointing takes a consistent snapshot while rollouts are in flight, then continues each one from its last safe point after a crash, without repeating work that has side effects and without waiting for stragglers.

The state a running rollout spreads across

One rollout is not one process. At any moment its state lives in several places:

WhereWhat must survive a crash
Environment server (Gym)Where the episode is in its protocol: which step runs next, which sessions it opened, and the results of steps already done
Agent server (Gym)The turn loop: the conversation so far, tool calls not yet answered, and session cookies
Resources server (Gym)Environment state per session, such as a counter, a database, or a document store that tools change
Policy model server (Gym)The token-free lineage of model calls, and which responses have not been delivered yet
Inference workers (training framework)Generated tokens, including the prefix of a generation still decoding
Training frameworkThe durable token store, the registry of dispatched rollouts, and the global checkpoint itself

Every rollout also has an identity that survives retries and restores: a stable rollout ID plus an attempt number. After a restore the rollout continues as the next attempt, and nothing of an older attempt may still be running anywhere.

What a correct checkpoint requires

  • One consistent cut. Every component's saved state describes the same moment of the same rollout.
  • No repeated side effects. A step that changes state is never run twice because of a restore.
  • Bounded latency. A checkpoint never waits for a generation or a slow rollout to finish; the controller can retire a straggler, which then restarts from its input.
  • Durable before published. Every component's files are complete and verified before the global checkpoint names them.
  • Retired work stops. Retiring an attempt stops its work everywhere before it returns, so nothing from a replaced attempt can still change state.
  • Nothing grows without an end of life. Every piece of state has an owner and an event that frees it; a restart does not count.
  • Fail closed. A server that cannot continue a rollout still takes part, so it can never silently produce a checkpoint that is wrong.

How it fits with NeMo RL

The training framework owns the global checkpoint transaction; Gym owns everything inside Gym.

  1. Prepare. The framework stops dispatching new rollouts, pauses its trainer and trajectory assembler actors until resume, and asks Gym to prepare. Gym brings every in-flight rollout to a safe point, in the order Gym defines, and reports any straggler it had to wait for.
  2. Commit. Gym writes each server's state into the framework's checkpoint directory. The framework saves its own state (token store, rollout registry, dataloader) alongside, and waits for results of rollouts that finished just before the cut.
  3. Publish, then resume. The framework publishes the checkpoint atomically and tells Gym to resume.
  4. Restore after a crash. The framework starts fresh Gym servers, restores Gym's state for the rollouts it will continue, and re-dispatches each of them as its next attempt, which continues from its last safe point.

Part 2

The v2 design

The rule that shapes everything: the component that decides the next operation owns the state needed to make that decision. The environment server owns where an episode is in its protocol. The agent owns its turn loop. The resources server owns environment state. The policy model server owns token-free lineage. The training framework owns tokens and the global checkpoint. No component persists another component's facts.

    3. Wait or replay: steps in flight at a checkpoint

    An episode is a sequence of steps. After each completed step the owner records a boundary: the next step and the results it needs. A checkpoint can always be taken at a boundary. The question is what to do with a step that is still running when prepare arrives. Each step has one of two modes.

    Why the two modes are not interchangeable. In wait mode the boundary after the step must carry the step's result, never "still pending". The resources server exports its state after the step finished, and the environment server may receive the reply slightly later. A record that said "pending" would make a restore re-run a possibly state-changing verification against state that already includes its effects. In replay mode either record is correct, because running the step again is declared safe.

    The resources server follows the same declaration for its own readiness: an in-flight verification it declared replayable does not block its prepare; one in wait mode does. Environment servers that verify in process need no resources server at all.

    7. Control API

    Every participating server exposes the same bearer-protected routes. Gym's checkpoint coordination calls them in the required order; the training framework calls the coordination.

    RouteValid in phaseEffect

    POST …/commitpreparedre-check readiness, write records then manifest; idempotent
    POST …/restoreidle, fresh processvalidate everything, install under the next attempt, stay closed

    Coordination order: prepare environment servers → policy model → agents → resources. Commit in any order. Every commit is scoped to the episodes the controller continues: those in flight, and each unclaimed restored episode under its replacement attempt. Resume resources → policy model → agents → environment servers. Retire callers before callees: environment servers → agents → policy model and resources together, each replying only after the attempts' work has stopped. After a commit writes its files, each participant also retires the restored episodes that are neither running nor in the commit's scope. Restore is all or nothing: if any participant fails, coordination retires the replacement attempts everywhere, which frees their restored state, and resumes every participant. The training framework restarts those rollouts from their input as later attempts.

    Before its own barrier, the training framework waits for the replies to its outstanding /run calls whose episodes no participant exported. Those episodes finished before prepare was ready, so their replies are already in flight. This replaces a completed-result acknowledgement protocol: Gym never holds a finished result waiting for an acknowledgement, and a lost reply can never block a checkpoint.

    8. Sandboxes: where they plug in

    A sandbox is session state that lives outside Gym's processes. Whichever server created it checkpoints it, through the same session hooks as any other state: a resources server that creates one sandbox per session in /seed_session, or an agent that runs tools, or a whole harness, in its own sandbox. Gym provides the hooks and the order; how a sandbox is saved and rebuilt (a snapshot, a paused sandbox, or something provider-specific) is up to the sandbox provider's implementation.

    PhaseResources server hookAgent hookWhat the sandbox implementation does
    preparenonenoneNothing. Agents park at a boundary, before a model call or after a tool round, and prepare stops agents before resources servers. Once prepare is done, no episode step is using a sandbox.
    commitexport_session_states(session_ids)export_agent_sessions(session_keys)Return what a restore needs to rebuild each session's sandbox as of this checkpoint.
    resume, no crashnonenoneThe live sandboxes carry on.
    restore after a crashrestore_session_states(states)restore_agent_sessions(sessions)In a fresh process, rebuild every session's sandbox or raise; the rollouts then restart from their inputs. Stop the sandboxes the crashed process left running.
    retireretire_session_state(session_id)retire_agent_session(session_key)Stop the retired attempt's sandbox.

    A server opts in with checkpoint_mode = "exported" (resources server) or checkpoint_sessions_supported = True (agent); servers that do not opt in stay restart-only. Both hook sets are asynchronous, and export takes every session at once, so a server can checkpoint all its sandboxes concurrently within the commit deadline. Any implementation has to meet these conditions:

    • A live sandbox is not a restore point. The episode keeps changing the sandbox after the checkpoint. Reconnecting to it after a crash would pair the checkpointed conversation with later sandbox state, so a checkpoint must keep the sandbox as it was, for example as a snapshot a new sandbox can start from.
    • Restore is all or nothing, and it must fit the restore deadline.
    • Commit cost grows with live sessions. Checkpoint sandboxes concurrently, with a bound, and avoid polling each sandbox separately.
    • Clean up what checkpoints keep. Snapshots or paused sandboxes must be deleted once no checkpoint the controller may restore refers to them, including after a crash, when the process that tracked them is gone.
    • Agents attached to a resources server's sandbox through its seed reply need the rebuilt sandbox's descriptor after a restore. Seeds are idempotent and admitted during a checkpoint, so the restored session's seed reply can carry it without a new call.
    • A harness running inside the sandbox must continue from the sandbox's filesystem after a restore: snapshots do not keep running processes.

    9. Retire: stop, then free

    Retiring an attempt is how a rollout leaves Gym without finishing: a straggler the controller gives up on, a restored episode it will not continue, or a row whose /run reply never arrived. The contract is simple to state and is what keeps every other table in Gym bounded:

    When retire returns, no work of the named attempts, or of earlier attempts of the same rollouts, is running anywhere in Gym, and everything Gym held for them is freed. Nothing Gym runs can send another request for the attempt, so no participant has to remember it afterwards.
    RuleWhy
    Callers before callees. Coordination retires environment servers, then agents, then the policy model and resources servers together. When a server's retire starts, everything that could still call it for this attempt has already stopped. A request the agent sent just before its own retire cannot reach the model server after the model's retire.
    Each participant stops before it acknowledges. It refuses new work for the attempt, cancels the attempt's running work, waits for it to finish within the request deadline, frees its state, and only then replies. Cancelling without waiting leaves work running that can still write. Waiting is what lets the refusal be temporary.
    The refusal lasts only as long as the stop. A request for an attempt that is being retired gets 409 stale_attempt. Once retire returns, the attempt is forgotten. A lasting record of retired attempts would grow with every rollout ever retired. After the stop there is nothing left that could send a request, so there is nothing to refuse.
    No retire while a checkpoint is open. A participant refuses retire while it is preparing, prepared or committed. It accepts retire when idle, and after a restore, where nothing is running yet. Otherwise retire can deadlock: the environment server's retire waits for the episode's final cleanup, that cleanup's /close_session waits for resume, and resume waits for the controller, which is waiting for the retire.
    Retire does not interrupt final cleanup. Once an episode has started its final cleanup, retire waits for it instead of cancelling it. A retire can reach an episode that is already finishing, for example when the controller retires a row whose reply was lost. Cancelling the cleanup would leak the agent and resources sessions it was closing. A shielded cleanup is not enough: a direct task cancellation still interrupts it.

    A straggler is handled by aborting, not by retiring into an open checkpoint: the controller resumes, retires the straggler, and prepares again. The rollout restarts from its input as its next attempt.

    10. Every resource has an end of life

    Long training runs make unbounded growth a correctness bug, not a tuning issue: a table that grows with every rollout, checkpoint or session ever seen eventually exhausts memory or disk, and a restart does not count as freeing it. Every piece of state Gym holds therefore has an owner and an event in the episode's normal life that frees it.

    • Memory is bounded by live work: episodes in flight, plus unclaimed restored episodes.
    • Disk is bounded by what has a named owner: checkpoints the controller retains, and capture data the training framework has not consumed yet. Each is freed by an explicit call, retire or delete, never by an age-based sweep.
    • The episode's owner frees what it created before it replies, on every path: success, failure, timeout, cancellation, retire, and an open checkpoint.
    • The host is left clean: a clean exit leaves no files, sockets, processes or sandboxes behind.

    The commit scope is the controller's statement of what it continues. Restored state waits for its replacement attempt. If the controller never re-dispatches an episode, nothing would ever claim it, and every later checkpoint would export it again. So after a commit writes its files, each participant retires the restored episodes that are neither running nor in the commit's scope. A controller that will continue a restored episode must name its replacement attempt in every commit until it re-dispatches it.

    Restore cleans up after the dead execution. It runs only in fresh processes: a policy model server that has served calls refuses it. It deletes capture files the dead execution left for the target attempt and later ones, so restoring the same checkpoint twice works. And it retires the ledgers of the attempts it continues, so the source attempt's files do not outlive the restore.

    11. Several workers per server

    Production servers run several uvicorn workers. Workers share one listening socket, so a request reaches whichever worker accepts it, while session state lives in the worker that created it. Two problems follow, one without checkpointing and one with it.

    • Session routing. Each new session is stamped with its worker's ID, inside the signed session cookie and inside the MCP session token a cookieless harness uses for tool calls. Each worker also serves the app on a private Unix socket, and a request for a session another worker owns is forwarded there unchanged. If the owner is gone, the request gets 410 instead of running against empty state. There is no central session table, so nothing grows with the sessions a server has served.
    • One participant per server. A control call reaches one arbitrary worker, so every server kind runs one participant across its workers: a coordinator in the main process and a worker link in each worker. Prepare is ready only when every worker is; commit gathers every worker's records into one file; an unregistered or lost worker blocks the checkpoint, and a worker that loses the coordinator stops itself.
    • Whole-episode state stays with the coordinator after a restore, and the worker that receives the replacement /run claims it; exactly one claim succeeds. With several workers, a claim that arrives while a checkpoint is open is refused like a new episode, and the caller retries.
    • The worker count is a deployment choice that may change between checkpoint and restore: from one worker to several, from several to one, or between different counts. Restored sessions are installed on live workers. Every router gets the alias table, from each old owner ID to its new worker, and the placement table, from session ID to worker, for sessions checkpointed with one worker, whose cookies name no owner. The placement table is replaced at each restore, so it is bounded by the sessions that restore installed.

    12. What the controller must do

    Gym's guarantees hold only if the training framework keeps its side of the contract:

    • Pause everything from prepare until resume: rollout dispatch, the trainer actors and the trajectory assembler actors. Nothing may retire, dispatch or consume rollouts while Gym is prepared or committed. That includes reading capture manifests and calling capture retire or delete, which a policy model server refuses with 409 while a checkpoint is open.
    • Abort, then retire. To retire a straggler, resume first, then retire, then prepare again.
    • After retire(N), dispatch attempt N+1 or nothing. Gym keeps no record that would refuse an older attempt.
    • Name every continued episode in each commit scope until its replacement is re-dispatched.
    • Retire a capture once it has been consumed or abandoned, and delete it once nothing can still write. Without these calls, capture files are never deleted.
    • Before its barrier, wait for replies to outstanding /run calls whose episodes no participant exported.
    • Retire only rows whose /run got no reply. A reply, even a failure, means the environment server already freed the episode's state.

    Architecture decision · 17 September 2026

    Partial-rollout checkpointing for NeMo-RL and NeMo Gym

    owner ansubramania · aligned with episode orchestration PRs #3482–#3492 · checkpoint ownership update · self-contained HTML, inline CSS/JS/SVG

    The episode-orchestration design moves the complete rollout lifecycle out of an agent server's /run method and into an episode processor. The processor owns resources and agent session setup, one or more /v1/responses activations, verification, cleanup, and the decision about what happens next. Checkpointing must therefore persist the episode boundary in the processor. Agent servers persist only the private session state needed to continue later /v1/responses activations. NeMo-RL still owns the global checkpoint transaction and validates the processor, agent-session, resources, model-lineage, and TransferQueue records as one compatible cut.

    Requirements for a recoverable checkpoint

    These requirements define when a checkpoint is safe to publish and restore. The walkthrough shows where each requirement affects normal execution, checkpoint preparation, saving, and recovery.

    System constraints

    • Gym must commit before the global checkpoint is published. A slow rollout therefore cannot block checkpointing indefinitely.
    • Durable token state remains a training-framework responsibility. The Gym draft stores lineage and staging coordinates, not token, mask, or log-probability arrays. A production checkpoint may be published only after the controller has made the referenced TransferQueue rows durable and has verified the join. That controller and actual queue durability are not part of PRs #2939–#2946.
    • Recovery starts from the latest published checkpoint. Gym keeps server state in memory and serializes it only during a checkpoint commit. After an unplanned crash, NeMo-RL re-dispatches any later in-flight work from its input.
    • One leased SingleController dispatches rollouts and coordinates checkpoints. A second controller cannot run concurrently.
    • The design must support large live execution sets. Shared-filesystem metadata operations cannot grow linearly with the number of rollouts.

    Identity

    A rollout keeps one identity across attempts.

    NeMo-RL assigns rollout_id before dispatch and preserves it across retries and restores. Each fresh dispatch or restore increments _ng_attempt_index. The attempt-qualified path (…-aN) identifies captured transport data, not the logical rollout. Every artifact, control call, and result carries the rollout ID and attempt index as separate fields.

    Servers reject stale attempts.

    A model, resources, or runtime mutation receives HTTP 409 when it carries an obsolete attempt index. Restore may add tombstones for abandoned call roots, but it cannot remove or reassign them. Final attribution ignores every tombstoned root.

    Admission and quiescence

    Closing a gate and testing admission happen atomically.

    The AdmissionLimiter grants a capacity permit only while the gate accepts work. Closing the gate atomically rejects or parks new callers. A caller waiting for capacity holds no permit and does not count as in flight. An admitted request remains in flight until its response and required custody updates are durable.

    Only policy model servers pause in the first milestone.

    Token-capture checkpointing first closes admission only on policy model-server instances backed by NeMo-RL generation workers. Stateless resources servers and verifiers retain no checkpoint state and do not need an admission API. Stateful-resources support later closes admission on those resources-server instances as well. Judge and simulator model-server instances remain open so accepted tools and verifiers can finish. Startup validation rejects environment traffic that targets a policy instance.

    A model-server pause must cover every FastAPI worker process.

    A pause request routed to one Uvicorn worker cannot close admission for the other workers that share the service port. The PR stack implements and tests a service-level coordinator protocol over a Unix-domain socket. Workers apply coordinator state and report acknowledgements plus local in-flight counts. The coordinator reports paused only after every expected worker has acknowledged the checkpoint ID and the summed count is zero. Production startup and control-URL routing are not wired yet, so a configured multi-worker server reports unmanaged and NeMo-RL must refuse checkpointing through it. Single-worker servers are the supported first integration.

    Prepare parks episode processors before it closes their dependencies.

    POST /ng-control/v1/episode-checkpoint/prepare changes active episodes to park_requested. Each processor finishes its current protocol operation, records an EpisodeBoundaryRecord, and blocks on an in-memory event. The boundary identifies the next protocol operation and every still-open agent and resources session. NeMo-RL prepares those component sessions and closes policy-model admission only after the processor has stopped issuing new calls. Judge and simulator model instances remain open while an accepted operation finishes.

    Resources mutations finish before state export.

    The resources middleware serializes mutations for each rollout attempt with an asyncio.Lock. Resources prepare closes admission, acquires each live session's lock, and exports that session after any accepted mutation releases the lock. New mutations receive 409 admission_closed. The first integration does not propagate admission leases or expose separate resources-admission routes.

    The controller decides what happens to unfinished rollouts.

    The Gym routes expose blockers and provide attempt-specific model abort, agent retirement, and resources retirement. Resources retirement is checkpoint-fenced and waits for that execution's mutation lock before it removes adapter state and the prepared snapshot. A future controller must decide whether all participant state for a straggler can be discarded. If an external effect cannot be rolled back or acknowledged, the controller must abort the global checkpoint rather than publish an incomplete cut.

    Ordering

    Generation workers stay available during prepare.

    Accepted generations must finish staging their output before Gym can drain. Pausing workers earlier would deadlock prepare. NeMo-RL may pause, checkpoint, or refit workers only after Gym commits and before the final resume.

    The future controller must finish finalizers before saving TransferQueue.

    Pausing Gym does not stop an RL-side finalizer that is already writing token rows. The training-framework integration must wait for those writes, publish a completed group before clearing staged rows, and then save the queue. This ordering is not implemented by the Gym stack.

    Each manifest is written last.

    A component writes payloads to temporary names, flushes them, and renames them before writing its manifest. The actor verifies every component digest before writing gym/manifest.json. The SingleController writes training_info.json last, renames the checkpoint atomically, and flushes the parent directory. A committed participant directory never changes.

    One explicit call resumes work in dependency order.

    Prepare, commit, and restore leave Gym paused. After the checkpoint is published and generation workers pass validation, NemoGym.resume opens resources admission and policy model admission, reconnects agent sessions and runtimes, releases parked episode processors, and finally reopens dispatch. A processor cannot resume before every session referenced by its boundary is usable.

    Durability and publication

    TransferQueue needs its own durable snapshot contract.

    The intended training checkpoint uses a fresh content-addressed path and restores it by the digest recorded in the global checkpoint. The Gym stack neither defines nor exercises that persistence operation; it only stores the coordinates that the controller must validate against the restored queue.

    Gym components publish immutable manifests after their payloads.

    The current draft writes one JSON payload per parked boundary or resources snapshot and copies token-free lineage files, then writes a digest-bearing manifest last. The episode-oriented design adds separate processor-boundary and private agent-session manifests. This makes torn writes and corrupt restore input detectable. Archive shards with a member index can replace per-rollout files later without changing the checkpoint APIs or state machine.

    Control operations are idempotent and fenced.

    Every actor method and control endpoint carries checkpoint_id and an absolute deadline. Repeating a phase for the same checkpoint returns the recorded result. A stale checkpoint ID cannot reopen traffic or replace files. A mutex in the NemoGym actor serializes checkpoint phase changes and live-execution snapshots. It prevents two checkpoint IDs from preparing concurrently, prevents commit, abort, restore, and resume from racing, and rejects invalid transitions such as commit before prepared. Participant I/O is deadline-bounded, and the lock-free checkpoint_status snapshot keeps progress observable while an operation is active.

    Restore

    NeMo-RL chooses one recovery action for each execution.

    An execution is already complete, resumes from an episode boundary, resumes from a full runtime snapshot, or starts again from its input. An execution marked transferred_to_rl cannot also have a continuation. The restored NeMo-RL registry decides whether work completed or failed. Gym does not make that decision.

    Gym restores participants paused; the controller verifies the full join.

    Each participant restores attempt-N state as attempt N+1 and remains closed until an explicit resume. The model participant rejects a non-fresh ledger namespace. The resources participant requires a fresh process that has not served stateful traffic. Agent servers restore only the sessions named by selected episode boundaries. Episode processors restore last, after the controller verifies their last model-call IDs, resources revisions, agent-session snapshots, and restored TransferQueue rows.

    An opaque harness requires a full runtime snapshot.

    A filesystem snapshot, sandbox identifier, or provider descriptor cannot restore an opaque harness by itself. A resumable snapshot includes the harness process tree and memory, the egress relay's pending requests and cached responses, and a provider compatibility fingerprint. At the prepare deadline, the runtime may freeze a forwarded but unfinished request as pending reissue. Restore tombstones the abandoned server-side call and sends a new request through the relay.

    The processor owns protocol state; servers own private session state

    The ownership rule is: the component that decides the next remote operation persists the state needed to make that decision. The episode processor decides whether to seed a session, invoke /v1/responses, verify, close, or return. It therefore owns the episode boundary. An agent server owns only state hidden behind agent_session_id that is needed to service a later activation. Resources and model servers continue to own environment state and model-call lineage.

    Do not persist the same mutable fact in two ownersThe processor may retain the request and response exchanged with an agent. The agent may retain an internal conversation or native thread cursor when that state is not supplied on the wire. It must be clear which copy is authoritative. A processor-supplied full conversation and an independently mutable agent-side conversation cannot both determine the next turn.

    State the agent server persists

    State that must not be checkpointed as application data

    Neither owner serializes active HTTP requests, asyncio tasks, semaphores, locks, clients, sockets, file descriptors, or arbitrary process memory. Prepare either waits for the current operation to reach a durable boundary, retires a restart-safe attempt, or delegates an opaque runtime to a provider that can snapshot and restore the complete process plus its egress state.

    Logical rollout and attempt identity

    rollout_id identifies the logical work across failures. attempt_index identifies one execution of that work. Restore never reactivates attempt N. It installs state for attempt N+1 and tombstones attempt N, so delayed HTTP requests from the old process receive 409 stale_attempt instead of mutating restored state.

    Episode processor execution state

    A boundary is the completed state after a whole protocol operation, not a separate execution state. While the processor is invoking the agent for activation 5, its boundary after activation 4 may remain available as a rollback point, but it is publishable only if every component still agrees with that earlier point. Prepare changes running to park_requested. The processor finishes the current operation, commits the next boundary, and then blocks on an in-memory event.

    The processor participant reports whether each parked episode has a committed boundary. Both a park without a boundary and a completed result that NeMo-RL has not durably acknowledged make ready_to_commit false. Agent-session and resources participants report their own matching state; the processor boundary does not substitute for those snapshots.

    If the deadline expires between boundaries, prepare fails without inventing a successful result. Retirement cancels the processor's outer /run task and any active component request, retires the referenced agent and resources sessions, and tombstones the attempt. Retirement is not durable result acknowledgement: a completed-but-unacknowledged episode continues to block publication.

    Checkpoint phase and admission state

    The control fence is per server process and per checkpoint ID. It prevents a stale or concurrent controller from committing, restoring, or resuming the wrong transaction. Repeating the same successful operation returns its recorded result. Most failed operations return to their entry phase. Model restore is deliberately different: a failure leaves both the limiter and the control fence in restore_failed_paused, so status remains observable and the same restore can be retried or explicitly resumed without admitting traffic by accident.

    Admission is a separate state machine. The policy model server changes from accepting to draining when prepare closes its gate. A request is prepare-safe only after durable completed custody, a durable failure, a validated active-prefix receipt, a no-generation exit, or complete pre-cut response egress. Response lifetime remains separate: a response that has not started is fenced until checkpoint resolution, while a stream that already started drains completely instead of entering a prefix cut. Missing workers, duplicate worker IDs, swallowed cancellation, and incomplete receipts fail closed. New requests receive 409 admission_closed. Resume reopens admission and releases fenced response egress after commit or restore.

    What the current Gym draft guarantees

    The model, agent-session, resources, and episode-processor participants preserve separate parts of one attempt-N cut and install them for attempt N+1 while traffic remains paused. Their manifests are separated by participant instance inside one controller-supplied directory. Active generation receipts bind immutable worker, model-call, frozen-buffer, inventory, and backend-snapshot identities. The production guarantee depends on a controller that checks every manifest and the matching TransferQueue snapshot before publishing one global checkpoint.

    How the components share checkpoint ownership

    The existing NeMo-RL SingleController owns the global checkpoint transaction, including a data-plane checkpoint barrier, native TransferQueue save and restore, rollout-recovery state, replay metadata, and atomic publication. The episode processor owns each externally dispatched /run lifecycle and the protocol boundary between resources seed, agent seed, /v1/responses activation, agent close, verification, resources close, and result return. Agent servers own private state behind agent_session_id. The policy model server owns admission and token-free lineage. Stateful resources servers own environment sessions, revisions, and exact-once mutation receipts. NeMo-RL #4093 must be updated to discover episode processors, order all participant routes, freeze actor-local membership, validate aggregate manifests, and acknowledge completed episode results.

    The processor boundary replaces the agent /run boundary

    The existing checkpoint draft places conversation, control phase, cookies, model-call identity, and resources revisions in AgentBoundaryRecord. Under episode orchestration, that record splits. EpisodeBoundaryRecord retains protocol position, request and response data, participant handles, cleanup obligations, and cross-component joins. AgentSessionSnapshot retains only private agent implementation state that cannot be reconstructed from the processor's request and response history.

    Normal rollout execution records restorable state

    Each component records the state it already owns during normal execution. The actor registers episodes. The episode processor records the latest completed protocol operation and the handles it still owns. Agent servers retain private session state across /v1/responses activations. The model server records token custody, generation workers stage tokens, and resources servers retain sessions. Checkpointing adds in-memory boundaries and receipts but no per-rollout filesystem writes during this phase.

    Prepare stops new work and reaches a recoverable boundary

    The intended NeMo-RL flow first stops new episode dispatch and asks each episode processor to prepare. Active processors finish their current protocol operation and park after committing a boundary. NeMo-RL then prepares every agent and resources session named by those boundaries and pauses policy-model admission. If a processor misses the deadline, references an uncheckpointable session, or reports an unsafe parked or completed state, prepare fails. A controller may retire a restart-safe attempt and retry, but Gym does not silently discard it.

    Save publishes only a complete checkpoint

    Gym accepts one controller-owned directory and writes frozen model, agent-session, resources, and episode-processor state into separate namespaces beneath it. Each component publishes a digest-bearing manifest last and remains paused until explicit resume. The controller must stop its rollout registry and TransferQueue writers, invoke those commits, save the queue, validate every artifact, and publish the global checkpoint. The current checkpoint draft implements the first three server participants under the older agent-owned /run boundary; episode orchestration requires the processor and agent-session split described here.

    Restore verifies each continuation before dispatch

    Replacement Gym processes restore model lineage, resources sessions, and agent sessions while admission remains closed. Episode processor boundaries restore only after those dependencies exist. The resources process must be fresh, and every participant requires a separate explicit resume. The controller verifies each processor boundary against the matching agent session, resources revision, model-call lineage, and restored token inventory. The first resumed policy call carries the verified attempt-N source capture key and parent model-call ID exactly once.

    Make the delivery representation explicit

    prefix: InlinePrefix | StagedPrefix | None

InlinePrefix:
  kind: "inline"

  kind: "staged"

    A root call has no prefix. A child call has exactly one representation. An inline prefix carries exactly prev_len token IDs and no staging chain. A staged prefix carries a nonempty staging chain and no token array. Both retain the same parent_call_id, prev_len, parent chain hash, and cumulative token hash. This replaces the current implicit contract in CaptureAdmission, where required_prefix_token_ids and staging_chain are independent optional fields and can both be populated.

    Do not store both forms as competing custody records

    Persisting cumulative token arrays and a staging chain for the same prefix creates two possible sources of truth. The forms can disagree, and repeatedly storing the cumulative array makes storage grow quadratically across a long multi-turn rollout. The durable ledger should record one authoritative custody location. Prefix delivery can then adapt that location to the backend: vLLM dereferences a staged chain itself, while an RL-side prefix materializer can fetch the same chain and send inline tokens to Megatron Inference.

    Megatron checkpoint recovery needs more than the schema change

    The explicit prefix union is a localized wire-contract cleanup. Continuing an unfinished Megatron generation is a larger cross-repository change. Megatron Inference needs a cut operation for an active request rather than only completed-call capture. NeMo-RL #3869 puts completed Megatron and vLLM calls on the same durable staging path, which the active cut should reuse. During restore, either Megatron gains a TransferQueue prefix source or NeMo-RL materializes the staged prefix and sends it inline before prefill.

    Why this approach fits Gym

    Gym already separates ownership across agent, model, and resources servers. The participant approach follows that boundary: shared infrastructure supplies identity, fencing, admission, manifest-last publication, and stale-attempt rejection, while each stateful implementation supplies only its codec and turn boundary. It preserves cheap drain-or-restart fallbacks, adds continuation one component at a time, and lets NeMo-RL coordinate the global checkpoint without importing environment-specific logic. The cost is more protocol surface and careful failure ordering. That cost is justified for expensive, long-running, stateful whitebox rollouts. Short stateless rollouts and opaque unsupported harnesses should continue to drain or restart.

    Assumptions the controller must enforce

    • Cross-component validation is an RL responsibility. The episode processor records last_committed_model_call_id, expected resources revisions, agent-session identity, and protocol position. Component manifests provide the corresponding model staging coordinates and private session state. Gym does not join them to a durable TransferQueue snapshot or choose the final recovery disposition.
    • The global commit marker is outside Gym. One Gym component can commit before another fails. The SingleController must select a checkpoint only after every required participant manifest validates.
    • Deadlines use synchronized wall clocks. Every request carries one absolute deadline_ts. Excessive clock skew can shorten or extend a participant's effective budget.
    • Only bounded waits enforce the deadline in the current stack. Prepare and model-drain paths consult deadline_ts. Component commit, restore, and resume still need explicit checks around potentially long filesystem or backend operations.
    • Checkpoint paths identify the same storage namespace. Server processes must see the controller-provided directory consistently. A remote or differently mounted worker cannot interpret a process-local path.
    • An unsuccessful mutation must not hide a committed effect. The resources middleware increments revisions only for successful HTTP responses. An environment that mutates state and then returns an error needs rollback or an explicit outcome record before it can claim continuation support.
    • Atomic resources activation is an environment callback contract. The shared participant passes the complete replacement set to restore_checkpoint_states. Each adapter must validate everything before replacing live maps; the framework cannot make a sequence of arbitrary environment mutations atomic on its own.
    • Completed results need a shared acknowledgement contract. The episode processor retains and reports completed-but-unacknowledged results, and retirement refuses to stand in for acknowledgement. NeMo-RL must durably accept the result before Gym can remove it from the recoverable live set. Component-session tombstone cleanup depends on the same ownership decision.
    • Capability discovery is necessary but not sufficient. A processor must commit a boundary after complete protocol operations, and each referenced stateful agent or resources session must implement its advertised snapshot contract. Inheriting checkpoint routes does not make a protocol resumable.

    Part 4

    From v1 to v2

    The v1 design planned an episode processor that owns the rollout lifecycle, and it described a Gym implementation in the eight-PR chain #2939–#2946. The episode processor landed on main as the environment server. v2 re-cuts the checkpoint stack around it and removes much of the machinery v1 needed, because a single owner of the episode protocol, plus a fixed participant order, makes a consistent cut without after-the-fact reconciliation.

    v1 was correct in intent but expensive to run and to build on. Most of its cost came from components reconciling each other after the fact. v2 removes that need, so the cost of a checkpoint stays small as rollouts grow in number and length:

    What stays the same

    • Identity: _ng_rollout_id and _ng_attempt_index, and the capture key r or r-aN. v1 refused a replaced attempt's requests forever; v2 refuses them only while a retire stops the attempt, because afterwards nothing of it is running.
    • Every control call carries a checkpoint ID and an absolute deadline; repeating a completed call returns the recorded result; a stale checkpoint ID cannot reopen traffic.
    • Manifests are written last, and a committed participant directory never changes.
    • Restore installs attempt N's state as attempt N+1, in fresh processes, and stays closed until an explicit resume.
    • Durable token storage and global publication stay with the training framework. Gym stores token-free coordinates.
    • Failure handling is fail-closed.

    Review feedback on the v1 implementation

    The 23 open review threads on #2939–#2946 fall into these groups:

    • Races between control operations (resume during prepare, delayed messages, wakeups crossing checkpoints): one lock serializes every transition, prepare re-checks its checkpoint after waiting, and resumed checkpoint IDs are remembered and refused.
    • Parent and identity propagation (agent middleware, the parent relay, headers versus URL prefixes): only the URL prefix remains, and the parent relay is gone.
    • Unfinished model calls saved too early: undelivered calls and their ledger rows are always left out.
    • Restore with live state, and stale attempts: every participant refuses restore with live state. Retire stops an attempt's work and frees its state before it replies, so no participant keeps a lasting fence.
    • Restored state that no replacement has claimed yet, lost by a second checkpoint: this concern still applied to v2 and is being fixed (gap 1 below).
    • Terminal sessions not reported to the checkpoint layer: resources servers get explicit session-start and session-end hooks for protocols that create sessions outside /seed_session.

    Open gaps

    1. Unclaimed restored state must survive a second checkpoint. Fixed: every participant exports it again, and a double-crash scenario covers it.
    2. The worker-side staging helpers that generation cuts need are not in Gym. Ported, and the fake worker in the process-level suite now continues cuts through them.
    3. Most resources servers have not declared a checkpoint mode, so they are restart-only. The five most used training verifiers (code generation, competitive coding, LLM-judge equivalence, math with judge, and GenRM comparison) now declare themselves stateless with replayable verification; others follow as they are audited.
    4. A replay-mode seed or verification that reaches a closed resources server fails instead of continuing. Fixed: replay-safe requests are admitted while closed and are not part of that checkpoint.
    5. Control traffic shares a connection pool with long-running /run calls. Fixed: control calls use their own pool.
    6. Environment servers and restart-only agents do not refuse more than one worker. Fixed.
    7. Constrained-decoding requests should restart instead of continuing a cut prefix.
    8. The framework needs a public list of the token-store keys a checkpoint retains.
    9. Agents, resources servers, and environment servers need one worker. Supported, with session routing; the worker count may change between checkpoint and restore.
    10. Lasting tables of retired attempts, retired sessions and checkpoint IDs. Fixed: retire stops, then frees, and only the most recent checkpoint IDs are kept.
    11. Restored state the controller never re-dispatches is kept forever. Fixed: a commit retires restored state outside its scope. An agent session orphaned when only the environment server crashed is still not freed.
    12. A duplicate /run for a running attempt can end the live episode. Idempotent /run is the fix.
    13. A harness that Gym does not manage can keep calling after its attempt is retired. Rejecting it needs a small, bounded list.
    14. Nothing tells a server when a checkpoint is pruned, so nothing frees the sandbox snapshots that exported state names. The controller should pass the retained checkpoint IDs.
    15. Host hygiene after a crash: coordinator socket files, session socket directories and temporary write files left by a killed process should be removed at the next start.
    16. Some inference backends serve the generation-cut route on a different root than their OpenAI API. They need a per-backend control URL, which must fail closed, not fall back, when a backend has none or the endpoint changes.
    17. Multi-worker policy servers. Supported. Sharded policy servers across Gym deployments, Megatron inline prefixes, and opaque runtimes remain future work.
