Partial-rollout checkpointing v2: how the pieces talk

Design v2 · environment-server architecture · draft for review, not yet merged

A long agentic rollout should survive a trainer checkpoint and a crash without being thrown away. This page walks through the lifecycle message by message: a normal episode, a checkpoint taken in place, a crash followed by a restore, a straggler that misses the deadline, and a generation that is cut mid-decode. Each step shows who sends what to whom and what every component's state machine is doing.

The rule that shapes everything: the component that decides the next operation owns the state needed to make that decision. The environment server owns where an episode is in its protocol. The agent owns its turn loop. The resources server owns environment state. The policy model server owns token-free lineage. The training framework owns tokens and the global checkpoint. No component persists another component's facts.

    3. Wait or replay: steps in flight at a checkpoint

    An episode is a sequence of steps. After each completed step the owner records a boundary: the next step and the results it needs. A checkpoint can always be taken at a boundary. The question is what to do with a step that is still running when prepare arrives. Each step has one of two modes.

    ModeWhile the checkpoint runsAfter a crashWhen to use
    wait (default)Prepare waits for the step to finish, then the episode parks at the boundary after it, with the step's result recorded. Past the deadline, the rollout is a blocker and the framework retires it.Continue after the step; it is not repeated.Always correct. The default for any step nobody has declared replayable.
    replay (optimization)Prepare does not wait: the episode counts as parked at the boundary before the step. The step keeps running; its result is held and acted on only after resume.The step is re-issued from the boundary before it.Steps that are safe to run again and do not change checkpointed state: idempotent seeds, pure or judge-based verification, policy calls.

    The environment server owns the episode's steps, so it decides. Whoever implements a step declares whether it may be replayed:

    Step implemented byDeclared byReplay allowed when
    The environment server itself (for example, verification computed in process)the environment-server implementationit declares the step safe to re-run
    A resources server (/verify, /seed_session)the resources server; the environment server reads the declaration at startupthe resources server declares it replay-safe (seeds are idempotent by contract); the environment server may still choose to wait
    An agent (one activation)the agent's own turn-loop boundariesalways covered: the agent parks itself, and an in-flight policy call is held
    A tool call that mutates environment state—never: accepted mutations finish before state is exported
    Why the two modes are not interchangeable. In wait mode the boundary after the step must carry the step's result, never "still pending". The resources server exports its state after the step finished, and the environment server may receive the reply slightly later. A record that said "pending" would make a restore re-run a possibly state-changing verification against state that already includes its effects. In replay mode either record is correct, because running the step again is declared safe.

    The resources server follows the same declaration for its own readiness: an in-flight verification it declared replayable does not block its prepare; one in wait mode does. Environment servers that verify in process need no resources server at all.

    7. Control API

    Every participating server exposes the same bearer-protected routes. Gym's checkpoint coordination calls them in the required order; the training framework calls the coordination.

    RouteValid in phaseEffect
    POST /ng-control/v1/checkpoint/prepareidle, preparingclose admission, then wait until ready or the deadline; report blockers
    POST …/retirepreparing, prepared, restored, idlediscard named attempts and fence them
    POST …/commitpreparedre-check readiness, write records then manifest; idempotent
    POST …/restoreidle, fresh processvalidate everything, install under the next attempt, stay closed
    POST …/resumeany non-idlereopen admission and release parked work; also the abort path
    GET …/statusanyphase, checkpoint ID, readiness report, and checkpoint mode
    POST /ng-control/v1/generation-cut (inference worker)—stage the prefix of each in-flight call and return a receipt

    Coordination order: prepare environment servers → policy model → agents → resources. Commit in any order, except that the model commit is scoped to the episodes the other participants exported. Resume resources → policy model → agents → environment servers. Restore is all or nothing: if any participant fails, every participant resumes empty and the training framework restarts those rollouts from their input.

    8. What changed from the earlier design

    • The environment server owns the protocol boundary. The earlier draft kept it inside the agent's /run. Legacy /run agents still continue, with the agent owning the whole episode.
    • Every episode step has a checkpoint mode. The owner records a boundary after each step, and a step in flight is either waited on (the default) or replayed after a crash when its implementer declares that safe. This covers slow verification, whether it runs in a resources server or in the environment server itself.
    • Checkpoints no longer wait for generations to finish. Undelivered responses are held; the agent is still at the boundary before the call, so the call is re-issued after a restore, and a generation cut can keep its prefix.
    • No completed-result acknowledgement. A result the training framework did not receive before its barrier restarts from input. This is always correct and removes a class of stalls.
    • Lineage continues through the ledger itself. Restored rows become the next attempt's ledger, so the first resumed call finds its parent normally; no one-shot parent header.
    • One control plane for every participant and one records file per participant, instead of a copy per component and one file per rollout.
    • Gym owns the participant order; the training framework calls Gym's checkpoint coordination instead of sequencing participants itself.
    • Unsupported means restart-only, never silent. A server that cannot continue a rollout still participates and blocks until that rollout is retired.
