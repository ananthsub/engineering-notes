NeMo Gym design audit
Design review · updated 3 September 2026

Reproducible NeMo Gym environment images

Why a working Gym environment cannot yet be treated as a reproducible customer artifact, what must be fixed beyond Python requirement pinning, and how environment code and customer evaluation data should meet at a versioned task contract.

Problem statement: today a Gym environment is a set of source directories, dependency files, server configuration, preparation code, task rows, and startup behavior. A Dockerfile can pin Python packages and still miss sibling source, downloaded tools, generated assets, the exact Gym runtime, task preparation, or the resources server’s expected row shape. The result may work in one checkout while changing on rebuild or installing more software when the container starts. A supportable customer artifact therefore needs two related contracts: an immutable environment image and a validated task dataset that declares exactly what the selected resources server consumes.

A reproducible image must freeze more than Python packages

The customer goal is simple: select an environment, build it once, move the image and evaluation data to another machine, inject deployment-specific configuration, and get the same executable environment and the same task inputs. Gym does not currently expose that as one complete contract. The normal runtime can discover components from a checkout, create component virtual environments, run setup code, prepare datasets, and pass loosely shaped row metadata to servers. Each behavior is useful for development, but each introduces an input that a conventional container build may fail to record.

The executable closure is implicit

A selected server can import another component directory, call a tool installed by startup code, depend on an operating-system package, or load an asset that is not named in requirements.txt. Copying only the selected directory and installing its Python lock can produce a valid build that fails at import or startup.

Startup can still mutate the image

The development path may create a virtual environment or download software when gym env start runs. That makes the effective runtime depend on network availability, package indexes, mutable upstream artifacts, and the user running the container.

Build and deployment inputs are mixed

Component selection affects image contents. Hosts, ports, API credentials, and service addresses should not. Without an explicit boundary, either secrets leak into serialized artifacts or harmless deployment changes force a different build identity.

Evaluation rows have no complete portable contract

Gym rows conventionally carry responses_create_params plus environment-specific fields, often under verifier_metadata. The resources server owns the meaning of those fields, but prepared artifacts currently canonicalize arbitrary JSON objects without validating the full row against the selected server’s schema.

Requirement pinning is necessary, but it covers only one layer

  • Base runtime: bind the OCI base digest, target platform, Python version, exact build tool, and operating-system packages inherited from the base.
  • Gym runtime: bind the exact Gym source and image recipe instead of installing whichever package revision is reachable later.
  • Component source: include and hash selected implementations plus transitive sibling imports and explicitly declared dynamic source dependencies.
  • Build outputs: move tool installation, asset download, code generation, and nested environment creation into declared build steps with verifiable outputs.
  • Runtime policy: fail when a required environment or asset is missing. A mounted configuration must not re-enable installation.
  • Configuration boundary: keep credentials, hosts, ports, URLs, and service topology out of image and lock identities.
  • Task boundary: version, validate, identify, and preserve the provenance of customer evaluation rows independently from the image.

Customers should supply environment code and task data through separate contracts

A customer-authored environment combines a resources server, an optional agent, configuration, dependency declarations, and a task schema. Gym should build that code into an image without embedding the customer’s evaluation rows. The same image can then evaluate any dataset that conforms to the published task schema.

Environment package

  • app.py implements tools, state, and verification.
  • task_data.py exports the Pydantic shape consumed by that environment.
  • A requirements file declares Python dependencies.
  • component.build.yaml declares additional source and build-time materialization.
  • YAML selects concrete agent, resources, and model server instances.

Prepared task artifact

  • A versioned envelope separates framework fields from environment-owned data.
  • Every row has a stable task_id.
  • responses_create_params contains the agent or model request.
  • task_data contains fields validated by the resources server schema.
  • Provenance records the source dataset, revision, split, and original row identity.

The task should be a stable input, not a rollout record

{
  "schema_version": "nemo-gym/task/v1",
  "task_id": "acme-eval:123",
  "responses_create_params": {
    "input": [{"role": "user", "content": "Question..."}]
  },
  "task_data": {
    "expected_answer": "42",
    "difficulty": "hard"
  },
  "provenance": {
    "dataset": "acme-eval",
    "revision": "2026-09-03",
    "split": "test",
    "source_id": "123"
  }
}

responses_create_params and task_data are task inputs. Rollout indexes, attempts, responses, rewards, trajectories, and other _ng_* fields are execution records and must not contribute to task identity. The existing per-server TaskData protocol is the right schema foundation because it can normalize legacy flat fields and verifier_metadata. The remaining product work is to make artifact preparation validate this complete envelope, export the selected environment’s JSON Schema, and translate task_data into legacy placement while older servers migrate.

The proposed customer workflow keeps code, data, and deployment separate

The new path moves installation out of startup

Build time

  • Build one Gym image from a source ref.
  • Install the core project from uv.lock.
  • Optionally run gym env prefetch for named configs.

Runtime

  • gym env start resolves each selected server.
  • setup_env_command() may create its venv and install dependencies.
  • The resolved config is placed in the child’s shell command before the process starts.

The current Dockerfile already has a useful bridge: it can prefetch selected server venvs during the image build. Prefetch is an optimization, not an immutable contract. The normal start path can still install, and main currently constructs child startup with serialized configuration in the command.

Build time

  • Resolve one concrete environment.
  • Compile each component to hash-complete requirements.
  • Verify Gym and component source digests.
  • Create every selected component venv in one image.

Runtime

  • Mount resolved config and task artifacts.
  • Start the same agent, resources, and model entrypoints.
  • Reuse prebuilt venvs as numeric user 65532.
  • Write temporary state under /tmp.

This is the smallest operational migration. It preserves Gym’s in-container process topology and keeps gym env start as the orchestrator.

Build output

  • One head-server image.
  • One image for each selected implementation.
  • A composition BOM with digest-pinned image references and instance names.

Operator responsibility

  • Project the same runtime config into every container.
  • Assign addresses, ports, probes, and service identities.
  • Provide Ray and start services in dependency order.
  • Compare image labels and BOM identities before launch.

Server code can keep its existing entrypoint, but deployment ownership moves out of RunHelper. The current implementation produces the BOM; it does not yet provide a controller that consumes it.

One concrete environment through the new workflow

Use one environment throughout: weather-eval selects simple_agent, example_single_tool_call, and openai_model. The model URL and API key are supplied only at runtime.

What the lock fixes

It records Python, uv, parent package versions, selected implementations, component content hashes, and hash-complete Python requirements. The builder refuses changed selected source.

What remains outside

The lock now binds the base image, platform, Gym source, Python, uv, selected components, and transitive sibling source. Operating-system packages remain a pinned-base responsibility. Components with startup downloads still need build manifests and offline certification.

Existing server APIs stay stable; packaging assumptions do not

No new /run, /verify, tool, or Responses API contract is required. A conventional server that has one relative entrypoint, self-contained source, lockable Python dependencies, and no startup installer can move to the packed path without code changes.

Estimate one component’s migration

Packed migration

  1. Keep existing YAML and entrypoint.
  2. Generate a strict lock for the exact composition.
  3. Fix dependency or source-closure failures.
  4. Build and mount prepared artifacts plus runtime config.

Additional split migration

  1. Provide an external Ray endpoint where required.
  2. Create services, probes, and addresses for each instance.
  3. Start the head and component containers.
  4. Validate cookies, callbacks, and cross-service routing.

The design buys repeatability by narrowing runtime freedom

What improves over main

  • Dependency resolution becomes an explicit, reviewable artifact.
  • Selected source changes invalidate the build.
  • Component venv creation moves to image construction.
  • Task rows gain stable identities and content verification.
  • Runtime config can arrive as a read-only file instead of shell arguments.
  • Images default to a non-root identity and writable temporary workspace.

What becomes harder

  • Mutable Git refs and per-component package indexes fail strict locking.
  • Every intentional source edit requires relocking.
  • Air-gapped operation requires assets and external tools to move into a build contract.
  • Each component gets a separate venv, which duplicates packages.
  • Split mode multiplies images and shifts orchestration to the deployer.
  • Cross-platform builds depend on a compatible, pinned base and BuildKit.
Image footprint: the packed-image smoke used a CUDA development base and copied separate Python and component environments into the runtime. This is not a general size benchmark, but it makes image-size measurement and shared-layer work a release consideration before broad deployment.

Full review audit

“Observed” items were reproduced against the reviewed snapshot. “Design gap” items follow a reachable code path but need a product decision or broader integration test. “Tradeoff” items are expected consequences rather than correctness bugs.

Runtime no-install policy is now monotonic

Resolved · tested

setup_env_command() chooses require-existing when either the image environment or mounted configuration requires it. A mounted allow-install value can no longer weaken a strict image.

Validation: the regression case combines image policy require-existing with mounted config policy allow-install and verifies that startup only activates the prebuilt environment.

Build contexts now include transitive sibling source

Resolved · container-tested

The lock infers imports rooted at the three component trees, follows them transitively, and merges explicit declarations for dynamic imports. Each source dependency receives its own digest. Packed and split contexts copy the closure while creating virtual environments only for selected runtime components.

Validation: all 175 lockable component directories produced a resolvable closure. Packed and split litellm_model images imported the sibling openai_model with a read-only root and networking disabled.

Common secret classes no longer affect lock identity

Resolved · tested

The shared secret predicate now covers passwords, secrets, credentials, authentication fields, cookies, private headers, tokens, and keys. Tests change each value independently and preserve the redacted configuration digest.

The lock now binds the base image and build toolchain

Resolved · container-tested

Strict locking rejects tag-only bases. The lock records the digest-pinned base, platform, Python version, exact uv version, and copied Gym source digest. Both Dockerfiles verify those inputs before dependency installation.

Copied Gym source is bound for every installation kind

Resolved · tested

The environment lock carries a top-level digest of the exact Gym source and image recipes copied into the build context. Image construction verifies that digest for registry, editable, VCS, and direct-URL parent installations.

Component startup installers require catalog migration

Partially resolved · migration remains

A versioned component.build.yaml now declares argv-only build steps and expected outputs. Build execution strips secret-shaped environment variables and fails when outputs are absent. The Codex agent demonstrates the migration, but other startup installers remain unconverted, so runtime capabilities deliberately report offline_runtime_installation: false.

Prepared artifacts now enforce runtime lock identity

Resolved · tested

Evaluation rejects a bound artifact when the runtime lock is absent or different. Images expose their embedded lock path. input_sha256 identifies original bytes for provenance, while data_sha256 and the artifact identity describe normalized task content.

Prepared artifacts do not yet validate a complete task contract

Design gap

Artifact preparation requires each row to be a JSON object, assigns or checks task_id, and canonicalizes the result. It does not require a versioned task envelope or validate environment-owned fields against the selected resources server’s TaskData schema. A customer can therefore create a content-valid artifact whose rows fail only after evaluation begins.

Remaining work: define nemo-gym/task/v1, export the selected environment’s JSON Schema, validate every row during import, and provide a compatibility translation for servers that still read flat fields or verifier_metadata.

The split BOM now renders a validated launch plan

Resolved · tested

gym env render-launch-plan validates schema and protocol versions, lock identity, image digests, head uniqueness, component and instance coverage, source digests, entrypoints, ports, and dependencies. It emits a secret-free orchestration contract and intentionally does not launch containers.

Rebasing onto today’s main requires one semantic merge

Observed · integration

The implementation started from cd6acf79…. Replaying it onto 98713f8e… merged every file except nemo_gym/cli/eval.py. Main added prepared-split declaration validation while the implementation added the artifact bypass. Both behaviors must remain in the resolved branch.

Reproduction: Git’s three-way merge reported one content conflict. After retaining main’s declaration validation and setting the artifact’s parent as the validation directory, the focused current-main regression set passed 713 tests and Ruff.

Container behavior is not covered by committed integration tests

Design gap

Local BuildKit validation now covers packed and split sibling imports, non-root execution, a read-only root, network-disabled startup, and identity labels. These checks are evidence for the branch but are not yet committed as a CI job.

Remaining work: add a bounded BuildKit job before treating container behavior as continuously certified.

Content hashing is intentionally coarse

Tradeoff

The Gym digest includes the full nemo_gym package and both image recipes. A packed-only Dockerfile change can invalidate split locks, and unrelated CLI edits invalidate every environment lock. Component hashes include tests and preparation files as well as runtime code. This is safe but increases rebuild frequency.

Split mode trades process convenience for independent rollout

Tradeoff

Per-server images can be scanned, promoted, scaled, and restarted independently. They also duplicate the Gym runtime and Python layers, require a registry push during every build, and make the deployer responsible for service discovery and shared runtime state.

Documentation and capabilities now state enforced guarantees

Resolved · Fern validated

The guide describes direct hash-checked installation, monotonic policy, source closure, artifact compatibility, and launch-plan rendering. Capabilities expose those individual guarantees and keep general offline runtime installation false until remaining component startup installers are migrated.

Remaining sequence to make this supportable

Define and enforce the customer task contract. Introduce a versioned task envelope, validate task_data against the selected resources server schema during artifact creation, export that schema for customer tooling, and preserve a compatibility path for legacy row layouts.
Migrate startup installers by component cohort. Add build manifests for components that download tools, assets, or nested environments. Pin every input and certify each converted startup path with networking disabled.
Clean the strict dependency blockers. Replace mutable VCS references and custom index directives with pinned, mirrorable artifacts or an explicit organization resolver policy.
Commit bounded BuildKit coverage. Keep one packed and one split sibling-import smoke in CI. Exercise non-root execution, read-only roots, missing-environment rejection, artifact mismatch, and launch-plan validation.
Replace local container evidence with CI permalinks. Keep the published source links and add immutable workflow evidence once the packed and split smoke jobs run in public CI.
