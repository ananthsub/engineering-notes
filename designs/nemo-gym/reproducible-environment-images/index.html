NeMo Gym design audit
Design review · 2 September 2026

Reproducible NeMo Gym environment images

How a resolved Gym environment becomes a lock, a packed or split image, immutable task data, and a runtime deployment—and what must change before existing servers can rely on that contract.

Short answer: the lock-first design is the right boundary for platform builds, and existing server entrypoints do not need a new API. It is not yet a drop-in replacement for today’s main image. The audit reproduced two release blockers: runtime config can downgrade the no-install policy, and selected-only build contexts omit sibling source required by many existing components. Static analysis classifies 114 of 174 configured components as likely no-code candidates; the remaining 60 need dependency cleanup, source-dependency handling, build-time setup, or a combination.

The new path moves installation out of startup

Build time

  • Build one Gym image from a source ref.
  • Install the core project from uv.lock.
  • Optionally run gym env prefetch for named configs.

Runtime

  • gym env start resolves each selected server.
  • setup_env_command() may create its venv and install dependencies.
  • The resolved config is placed in the child’s shell command before the process starts.

The current Dockerfile already has a useful bridge: it can prefetch selected server venvs during the image build. Prefetch is an optimization, not an immutable contract. The normal start path can still install, and main currently constructs child startup with serialized configuration in the command.

Build time

  • Resolve one concrete environment.
  • Compile each component to hash-complete requirements.
  • Verify Gym and component source digests.
  • Create every selected component venv in one image.

Runtime

  • Mount resolved config and task artifacts.
  • Start the same agent, resources, and model entrypoints.
  • Reuse prebuilt venvs as numeric user 65532.
  • Write temporary state under /tmp.

This is the smallest operational migration. It preserves Gym’s in-container process topology and keeps gym env start as the orchestrator.

Build output

  • One head-server image.
  • One image for each selected implementation.
  • A composition BOM with digest-pinned image references and instance names.

Operator responsibility

  • Project the same runtime config into every container.
  • Assign addresses, ports, probes, and service identities.
  • Provide Ray and start services in dependency order.
  • Compare image labels and BOM identities before launch.

Server code can keep its existing entrypoint, but deployment ownership moves out of RunHelper. The current implementation produces the BOM; it does not yet provide a controller that consumes it.

One concrete environment through the new workflow

Use one environment throughout: weather-eval selects simple_agent, example_single_tool_call, and openai_model. The model URL and API key are supplied only at runtime.

What the lock fixes

It records Python, uv, parent package versions, selected implementations, component content hashes, and hash-complete Python requirements. The builder refuses changed selected source.

What remains outside

The base image identity, operating-system packages, sibling source dependencies, component startup downloads, deployment topology, and secret-bearing runtime configuration need separate contracts.

Existing server APIs stay stable; packaging assumptions do not

No new /run, /verify, tool, or Responses API contract is required. A conventional server that has one relative entrypoint, self-contained source, lockable Python dependencies, and no startup installer can move to the packed path without code changes.

Estimate one component’s migration

Packed migration

  1. Keep existing YAML and entrypoint.
  2. Generate a strict lock for the exact composition.
  3. Fix dependency or source-closure failures.
  4. Build and mount prepared artifacts plus runtime config.

Additional split migration

  1. Provide an external Ray endpoint where required.
  2. Create services, probes, and addresses for each instance.
  3. Start the head and component containers.
  4. Validate cookies, callbacks, and cross-service routing.

The design buys repeatability by narrowing runtime freedom

What improves over main

  • Dependency resolution becomes an explicit, reviewable artifact.
  • Selected source changes invalidate the build.
  • Component venv creation moves to image construction.
  • Task rows gain stable identities and content verification.
  • Runtime config can arrive as a read-only file instead of shell arguments.
  • Images default to a non-root identity and writable temporary workspace.

What becomes harder

  • Mutable Git refs and per-component package indexes fail strict locking.
  • Every intentional source edit requires relocking.
  • Air-gapped operation requires assets and external tools to move into a build contract.
  • Each component gets a separate venv, which duplicates packages.
  • Split mode multiplies images and shifts orchestration to the deployer.
  • Cross-platform builds depend on a compatible, pinned base and BuildKit.
Measured footprint: the reviewed one-environment lock was 864,312 bytes. A local packed-image smoke using a CUDA development base produced a 23,977,897,062-byte image; the copied Python and Gym/component environments contributed about 4.17 GB of additional layers. This is one build, not a general benchmark, but it makes image-size and shared-layer work a release consideration.

Full review audit

“Observed” items were reproduced against the reviewed snapshot. “Design gap” items follow a reachable code path but need a product decision or broader integration test. “Tradeoff” items are expected consequences rather than correctness bugs.

Runtime config can turn installation back on

Observed · release blocker

setup_env_command() reads runtime_install_policy from resolved config before consulting NEMO_GYM_RUNTIME_INSTALL_POLICY. A mounted config containing allow-install therefore overrides the packed image’s require-existing environment setting.

Reproduction: image policy require-existing + mounted config policy allow-install returned a command containing uv venv. Source: nemo_gym/cli/setup_command.py:235-253 in the review snapshot.

Selected-only build contexts omit required sibling source

Observed · release blocker

The context copier includes only implementations selected by the environment lock. Existing components frequently reuse sibling implementation code. For example, litellm_model imports openai_model. A lock selecting only litellm_model copies its directory but omits openai_model. The same issue affects packed and split images.

Reproduction: a generated representative context reported selected_present=True and required_sibling_present=False. Static import analysis found 42 configured components with cross-component source imports. Source: nemo_gym/environment/image.py:181-194 in the review snapshot.

Common secret names still affect lock identity

Observed · security contract

Lock redaction delegates key detection to the existing predicate, which matches token, key, and header. Plain values under password, client_secret, or credential are not masked. The lock does not print those values, but its identity changes with them, contradicting the claim that secrets are excluded from lock identity.

Reproduction: changing api_key, token, or header preserved the digest; changing password, client_secret, or credential changed it. Source: nemo_gym/environment/lock.py:145-173 and the public secret-key predicate.

The base image is an input but not part of the lock

Design gap

Strict mode accepts a mutable base tag. The lock identity and labels remain unchanged when that tag resolves to different bytes. The documentation recommends a digest, but the builder does not require one or record the resolved base digest.

Resolution: add the OCI base digest and platform to the environment lock, reject tag-only bases in strict mode, and carry the digest into the composition BOM and image labels. Source: nemo_gym/environment/image.py:250-281 in the review snapshot.

Registry Gym identity does not bind the copied Gym source

Design gap

Editable installs receive a Gym source digest. Registry installs do not. Image construction still copies source_root/nemo_gym and builds a wheel from it, while verification checks only that the version string matches. A different source tree with the same version can therefore enter the image.

Resolution: either build registry locks from a hash-pinned wheel without a source checkout, or always hash the source tree that will be copied. Source: nemo_gym/environment/image.py:137-146 and nemo_gym/environment/lock.py:217-275 in the review snapshot.

No-install covers Gym venv setup, not component startup setup

Design gap

The runtime policy gates setup_env_command(). It does not stop an agent or resources server from downloading Node, installing an external tool, creating a nested venv, or fetching assets in model_post_init() or __init__(). Static analysis found 14 configured components with such startup hooks. The public Codex setup path downloads a Node distribution.

Resolution: define component build hooks and declared assets, execute them in the build stage, and add a strict startup guard or network-disabled smoke for certified components.

Prepared-artifact provenance is recorded but not enforced

Design gap

The manifest may carry an environment-lock identity. Runtime loading verifies the artifact’s own digest, row count, canonical encoding, and split, but does not compare that identity with the running image’s lock. The source_sha256 field also duplicates the canonical output data hash rather than preserving the input file’s byte identity.

Resolution: compare non-null artifact lock identity with the mounted or embedded environment lock before server startup, and clarify whether source identity means original bytes or normalized task content. Source: nemo_gym/environment/artifact.py:102-174 and nemo_gym/cli/eval.py:415-425 in the review snapshot.

The split BOM has no runtime consumer

Design gap

gym env build-images pushes images and writes a digest-pinned composition BOM. No Gym command parses that BOM to validate labels, materialize services, start containers, or check readiness. Operators must independently reconstruct ports, addresses, Ray connectivity, startup order, and health policy from runtime config.

Resolution: keep the BOM deliberately build-only and publish a deployment adapter contract, or add a small validator/renderer that turns BOM + runtime config into an orchestrator-neutral launch plan.

Rebasing onto today’s main requires one semantic merge

Observed · integration

The implementation started from cd6acf79…. Replaying it onto 98713f8e… merged every file except nemo_gym/cli/eval.py. Main added prepared-split declaration validation while the implementation added the artifact bypass. Both behaviors must remain in the resolved branch.

Reproduction: Git’s three-way merge reported one content conflict. After retaining main’s declaration validation and setting the artifact’s parent as the validation directory, the focused current-main regression set passed 713 tests and Ruff.

Container behavior is not covered by committed integration tests

Design gap

The unit suite checks lock models, generated commands, source verification, and Dockerfile text. Most image builds are mocked. The local smoke demonstrated a packed image starting as non-root with networking disabled, but CI does not currently replay that path or test a cross-component server.

Resolution: add one small BuildKit smoke that builds a packed image, rejects a missing venv, starts with a read-only root, and exercises a declared source dependency. Add a split-image import/start smoke before calling split support generally compatible.

Content hashing is intentionally coarse

Tradeoff

The Gym digest includes the full nemo_gym package and both image recipes. A packed-only Dockerfile change can invalidate split locks, and unrelated CLI edits invalidate every environment lock. Component hashes include tests and preparation files as well as runtime code. This is safe but increases rebuild frequency.

Split mode trades process convenience for independent rollout

Tradeoff

Per-server images can be scanned, promoted, scaled, and restarted independently. They also duplicate the Gym runtime and Python layers, require a registry push during every build, and make the deployer responsible for service discovery and shared runtime state.

Documentation overstates two current guarantees

Design gap

The draft says image construction populates a temporary wheelhouse, but installation now goes directly through uv pip install --require-hashes --no-deps. It also says deployment addresses are excluded from lock identity, while server configuration—including ordinary URL and host fields—feeds the redacted config digest. The capability output reports offline runtime installation even though policy downgrade and component startup hooks remain.

Recommended sequence to make this supportable

Make strict policy monotonic. An image-level require-existing setting must win over runtime config. Add a regression test using a mounted config that requests allow-install.
Define the source closure. Add explicit component source dependencies, derive them conservatively, or temporarily copy and hash the complete component trees. Test a real sibling-importing model and resources server in packed and split modes.
Bind every build input. Put the resolved base-image digest in the lock. Hash copied Gym source for registry and editable installs. Verify the build-stage uv version recorded by the lock.
Separate runtime config from build identity. Define which server fields affect binaries and which are deployment-only. Expand secret-name redaction and prove password, client-secret, credential, headers, tokens, and arbitrary secret URLs do not affect or appear in locks.
Add build hooks and immutable assets. Give components a declarative way to install external tools, nested environments, and datasets during image construction. Record their digests and certify startup with networking disabled where the environment permits it.
Enforce artifact compatibility. Compare prepared-artifact provenance with the running lock before servers start, or explicitly document why cross-lock reuse is allowed. Rename or fix source_sha256.
Choose the split ownership boundary. Either ship an orchestrator-neutral BOM validator/renderer or state that split mode is a low-level build primitive. Document Ray, addressing, health checks, cookie routing, and startup order.
Rebase and certify in layers. Resolve the one current-main conflict, land secure config handoff and packed mode first, add a BuildKit smoke, then certify component cohorts. Treat split mode as a later milestone after source closure and deployment ownership are explicit.
